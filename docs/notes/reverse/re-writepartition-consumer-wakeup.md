# RE: WRITE-PARTITION — consumer wakeup: точные структуры, событийная таблица, разрешение парадокса «успех без записи»

Дата: 2026-10-24. Бинарь: `/home/musin/firmware/extracted/IMAGES/da2_oplus.bin`
(356296 B, ARM32, VA = file offset + 0x40000000). Инструмент: capstone (ARM) из
`/home/musin/mtkclient/.venv` (`/tmp/opencode/disasm.py`). Контекст:
`re-writepartition-silent-skip.md` (обязательно), `re-write-chain.md`,
`re-write-partition-offset.md`.

## TL;DR

1. **«DMA-callback» — это не callback, а ПОЛНОЦЕННЫЙ ПОТОК мини-RTOS.**
   `0x400096d8(name_id, entry, arg, prio, stack_size)` = **task_create**
   (5-й аргумент — stack size 0x10000, malloc'ится в TCB+0x30/+0x34; prio=0x10
   кладётся в TCB+0x14). `0x400097e8` = **task_start** (перевод в ready,
   вставка в ready-list, reschedule). Диспетчер — `0x40009a10` (ready-массив
   `0x40069ED0` по 8 байт на приоритет, битмаска `0x4006A034`, current-TCB
   `0x40067CD8`, переключение `0x40000f04`). Consumer **создаётся и
   стартуется до data-цикла** (0x4003076c/78) — «движок не запущен»
   исключено, если верить коду старта.
2. **Engine-2 ЖДЁТ потребителя.** После data-цикла: `0x40030788`
   `0x400093b0(ctx2+0xA8, -1)` (семафор «consumer exit» — его постит ТОЛЬКО
   выход consumer'а, `b 0x4002f758` @0x40030108 c r1=1) и `0x40030798`
   `0x400093b0(ctx2+0xC4, -1)` (семафор «producer exit» — постит продюсер
   через `0x4002f758(ctx2,0)` @0x400304b4). «Download_data end.»
   (0x4004f48a, печать @0x40030804) идёт **после обоих ожиданий** ⇒ факт
   печати в live-логе доказывает: consumer-таск дошёл до своего exit'а.
3. **Дамп из живой сессии НЕ описывает write-движок.** Главное:
   - `[ctx2+0x1C]` в write-структуре — это поле **sem.max** семафора
     record0.empty (sem @ctx2+0x14 создаётся `0x40009334(sem, init=0, max=1)`,
     `str r2,[sem+8]` ⇒ `[ctx2+0x1C] == 1` всегда после open). В дампе там
     `0x10000` — значение, которое write-код в это поле **не пишет никогда**.
   - `[0x4006E7CC]`/`[0x4006E7D0]` — глобальные слоты, **реиспользуемые
     read-движком** (ссылки 0x400309a4/0x40030ad0/0x40030c70 — тот же layout:
     +0xA0/+0xA4 индексы, record-шаг 0x4C, семафоры +0x14/+0x30). Любой
     readback (а он делался — «[UFS] switch to section» появляется при
     чтениях) **перетирает** оба слота и всё состояние пайплайна.
   - `ctx2+0x10` (record0.fill) и `ctx2+0x1C` **не инициализируются** open'ом
     (`0x4002f5f8` пишет только +0/+4/+8/+0xC/+0x50/+0x54/+0x58/+0x9C/+0xA0/
     +0xA4/+0xE0/+0xE4 и семафоры) — «0x800000» в +0x10 = накопление
     producer'а (zero→add), «0x10000» в +0x1C — стёк из другой фазы.
   ⇒ **все выводы «handle нулевой ⇒ init не вызывался» из этого дампа
   недостоверны**: дамп, скорее всего, снят после readback и описывает
   read-pipeline.
4. **Статически «тихий не-успех записи» практически исключён** на healthy-путях: единственный выход consumer'а **без** вызова писателя — `[E0]<0`
   при первом пробуждении (0x4002ffb4). Любой другой выход проходит через
   `0x4002f804`, который при `ctx1[0]!=0` **безусловно** вызывает bulk-init
   `0x4002d5a8`, а init **всегда** пишет `[handle+0x34] = [0x58+0x10]` либо
   `0x4006E6A0` (указатель дефолтного region-списка, `0x4002d938`) — то есть
   **ненулевое** слово. Даже вызов с len==0 инициализирует хэндл.
5. **Решающий шаг (дешёвый):** повторить WRITE-PARTITION и снять дамп
   **сразу после ответа команды, ДО любого чтения**, по точному списку полей
   (§5) + поставить маркер-патч F5 (§6, байты верифицированы), который
   пишет длину последнего обработанного чанка в `0x4006E7C8`. Три числа
   (`0x4006E790+0x34`, `[ctx2+0xA0]`, `0x4006E7C8`) однозначно выбирают
   между: «consumer не просыпался» / «просыпался, но len==0» / «писал, и
   проблема ниже (UFS-очередь/section)».

### 1.2 Структуры

**TCB (0x64 байт):** +0x00 magic/"dth…", +0x04/+0x08 ready-node (ldm/stm
парами в `0x400097b8`: `[tcb+4..0xB]`), +0x0C wait-node, +0x14 **prio**,
+0x18 **state** (0 created / 1 ready / 2 running / 3 waiting), +0x1C =1,
+0x24/+0x28 = 0, +0x30 **stack base**, +0x34 **stack size**, +0x38 **entry**,
+0x3C **arg**, +0x44 name[0x20].

**Semaphore (0x1C байт):** +0x00 magic "evnt", +0x04 flag (байт, = init),
+0x08 **max**, +0x0C waitqueue {magic "wati", head→self, tail→self, count}.

**Очереди готовности:** `0x40069ED0` — 2 слова на приоритет (head/tail),
`0x4006A034` — битмаска активных приоритетов, `0x40067CD8` — current TCB,
`0x40069EC8` — список всех TCB.

## 4. Разбор гипотез

**(а) consumer проснулся, `[record+0x10]==0` → exit 0 без записи.**
Возможна ТОЛЬКО если consumer никогда не видел заполненного record0.
Статически пара post/wait lockstep'ная (post #11 → wait #6/16), рассинхрона
нет: семафоры счётные (max 1), флипы синхронны. Но! Первый вызов
`0x4002f804` (с любым len, base≠0) **инициализирует bulk-хэндл** — а дамп
говорит «не инициализирован». Для чистого (а) нужно, чтобы consumer вообще
не доходил до `0x4002ffd8` — т.е. exit по `[E0]<0` (см. (в')).

**(б) `0x4002f804` всегда с len==0.** Опровергнут статикой для ПЕРВОГО
вызова: даже len==0 при ctx1[0]=1 проходит 0x4002f984 → init ⇒ `[h+0x34]≠0`.
Однако len==0 **на последующих** вызовах даёт ровно наблюдаемую ветку
`0x4002fed0 → ret 0` («успех» без записи). Так что гибрид «первый вызов
был, но не в этом состоянии» снова упирается в дамп.

**(в) consumer не просыпался / не запущен, engine-2 «не ждёт».** Опровергнуто:
engine-2 **ждёт** +0xA8 (0x40030788) и +0xC4 (0x4003079c) ДО close/commit;
+0xA8 постит только consumer-exit; печать «Download_data end.» идёт после
обоих wait'ов и не выполняется на error-путях (0x40030828 → ret 0xC0040002
без этой печати). Так что host-успех ⇒ consumer exit был.

**(в') consumer проснулся ОДИН раз, увидел `[E0]<0` и молча вышел** —
единственный статически возможный «zero-work success». Но все писатели
`[E0]` в цикле пишут 0 (успешный обмен 0x4003053c → 0; успешный recv → 0),
а recv-ошибка (0x400303a8 bne) уходит в ветку с печатью (0x4004f42b,
loglevel≤4) — в DEBUG-логе чисто. ⇒ (в') требует «невидимой» отрицательной E0 — низкая
вероятность, но проверяется одним числом (дамп +0xE0 сразу
после команды).

**(г) — новая, самая вероятная: дамп описывает не то состояние.** После
WRITE-PARTITION выполнялись чтения; read-движок переиспользует
`[0x4006E7CC]/[0x4006E7D0]` (0x400309a4/0x40030ad0/0x40030c70) и, возможно,
пишет `+0x1C = 0x10000` (размер транспортного чанка). Тогда: write мог
**и инициализировать хэндл, и(dispatch) отправить данные в UFS-очередь**, а
«флеш не меняется» — проблема УЖЕ ниже (очередь `0x400200ec` не
завершается/не сбрасывается, неверный section/LU, отсутствие flush для
dev-type 0x31 в `0x4002f3d8` — там UFS-тип даёт **молчаливую ошибку**
flush-операции, результат которой игнорируется).

## 5. Решающий live-эксперимент (дешёвый, однозначный)

Сессия с DEBUG-логом. Порядок: WRITE-PARTITION (para, pre_erase=NO,
0x80000, патчи F1/F3 + остальные как обычно) → **сразу после ответа
команды, НЕ делая ни одного чтения**, прочитать:

1. `[0x4006E7CC]` → ctx1: слова +0x00, +0x10, +0x14, +0x18;
2. `[0x4006E7D0]` → ctx2: слова +0x08, +0x0C, +0x10, +0x14, +0x1C, +0x30,
   +0x4C, +0x60, +0x9C, +0xA0, +0xA4, +0xA8, +0xC4, +0xE0, +0xE4, +0xE8;
3. `0x4006E790` слова +0x00, +0x04, +0x08, +0x18, +0x28, +0x2C, +0x34;
4. `0x4006E7C8` (слово), `0x4006E6A0` (+8/+0xC — размер дефолтного
   region-списка), `[ctx1+0x24]`→0x58-структура: байты +0..+3 и слово +0x10.

**Дерево решений:**

| h+0x34 | ctx2+0xA0 | 0x4006E7C8 | Диагноз | Следующий шаг |
|---|---|---|---|---|
| ≠0 | ≥1 | ≠0 | consumer работал, писал; проблема в UFS-слое | инструментировать `0x400200ec`/очередь; проверить `[0x40056A70]`, `[UFS] switch to section`, завершение очереди (IRQ) |
| ≠0 | ≥1 | 0 | consumer работал, но все len<0x100 (или маркер не встал) | смотреть record +0x10/+0x4C |
| 0 | 0 | 0 | **consumer не обработал ни чанка** — wakeup-проблема | копать scheduler: task_start ret, состояние TCB consumer'а (`[tcb+0x18]`), стэк |
| 0 | ≥1 | 0 | consumer просыпался, но все вызовы len==0/или хэш-ветка | дампить `[E0]` в момент, record.fill |
| любой | — | — | `[E0]<0` | искать источник отрицательного E0 (recv/обмен) |

Дополнительно (бесплатно): сразу после команды прочитать TCB consumer'а —
его адрес возвращается `0x400096d8`… хосту он недоступен напрямую, но TCB
ищется в списке `0x40069EC8` (поле +4/+8), `[tcb+0x38]==0x4002ff78` — и
`[tcb+0x18]` покажет состояние (2=running/3=waiting ⇒ где застрял).

## 6. Маркер-патч F5 (байты верифицированы по файлу)

Назначение: записать **len последнего чанка** в слово `0x4006E7C8` в момент
входа в writer-dispatch, не меняя семантики (r0/r1 к вызову `0x4002e4b0`
сохраняются, F3 дальше гасит результат).

| VA | до (файл) | инструкция | после (файл) | инструкция |
|---|---|---|---|---|
| `0x4002F858` | `04 00 A0 E1` | `mov r0, r4` | `00 10 86 E5` | `str r1, [r6]` (r6=0x4006E7C8, r1=len) |
| `0x4002F85C` | `0A 10 A0 E1` | `mov r1, sl` | `04 00 A0 E1` | `mov r0, r4` |

После этого слово `0x4006E7C8 = (len & 0xFFFFFF00) | magic_result_byte0`
(F3 даёт byte0=0). `0x4006E7C8+4 = 0x4006E7CC` (указатель ctx1) — не
затрагивается. Совместимо с F1/F3; снимается перед продакшн-записью.

Дополнительно, если (h+0x34==0, A0==0): «starting-point» проба — патч
`0x40009430`-вызова producer'а не нужен; вместо этого прочитать
`[0x4006A034]` (битмаска готовых) и список `0x40069EC8` сразу после
завершения команды: если consumer-TCB в состоянии 3 (waiting) на
record-семафоре — пост «пролетел» мимо; если 1 (ready) и не выбирается —
проблема диспетчера приоритетов.

## 7. Предупреждения по интерпретации лога

- В логе сессии `DwnFile→OK@0x80000` (размер файла), а дамп даёт
  target=0x800000 ⇒ **дамп и лог — из разных запусков** (или в дамп-сессии
  писалось 8 МБ). Сверяйте target (`[ctx1+0x10]`) с ожидаемым размером в
  каждом прогоне.
- `ctx2+0x10` НЕ инициализируется open'ом — мусор там легален до первого
  заполнения слота producer'ом.
- Строка `get verified image name failed but could use original name.`
  (0x40041b9b) печатается из **парсера WRITE-PARTITION** (0x40002490 и др.),
  а НЕ из consumer'а — не использовать её как признак работы `0x4002f804`.
- «[UFS] switch to section» при записи может легально молчать, если
  section уже выбран (=3) — отсутствие печати не доказывает «записи не было».

## 8. Фиксы, готовые к применению после диагностики

- **F4 (host-side, делать в любом случае):** в `xml_lib.upload()` первый
  in-loop ack = `ack_value(length)` (не 0), последующие — `ack_value(0)`;
  устраняет класс race'ов с target==0 (`0x40030250 beq` — весь приём
  пропускается, оба слота постятся пустыми, consumer выходит «успешно»,
  НО visible: target==0 ⇒ заполнения нет ⇒ `[ctx1+0x18]` = 0 — легко
  отличить в дампе).
- Если подтвердится «писали, но флеш чист» — следующий слой:
  `0x400200ec` (постановка в очередь UFS) и завершение транзакций;
  кандидат на «потерянный» шаг — flush для UFS: `0x4002f3d8` для
  dev-type 0x31 возвращает 0xC0040009 **молча** (результат в `0x4002fed0`
  не проверяется) — если семантика flush обязательна для коммита
  очереди, это прямой кандидат на байтовый патч (маршрутизировать 0x31 в
  реальный UFS-flush либо NOP-нуть проверку и вызвать UFS-завершение).

## 9. Конкретный следующий шаг

**Live-проба №1 (приоритет):** сеанс с DEBUG-логом; применить F1/F3 + F5;
WRITE-PARTITION para (pre_erase=NO, 0x80000); **немедленно** (до любого
чтения) прочитать поля из §5 (список из ~25 слов); присмотреть stderr-лог
DA. Интерпретация по таблице §5. Результат однозначно выбирает между
«wakeup», «len==0», «пишем — ищи в UFS-слое».
