## TL;DR verdict

| handler | gate inside handler | reachable targets | exploitability | bricking risk |
|---|---|---|---|---|
| CMD:WRITE-EFUSE `0x40005C20` | **NONE** (only `len==0x200` on the payload) | **arbitrary 32-bit write anywhere the DA address space maps** (efuse controller regs, DA RAM globals, SoC MMIO) via the XML `<debug>/<write>/<extra>/<option address=…>` path — **proven in emulation, rc=0** | **EXPLOITABLE** — write-what-where; `g_oplus_auth_status ← 5` demonstrated | **YES** — can blow real efuse words (`0x11C10060` SBC word written with 0xFFFFFFFF in emu) |
| CMD:READ-EFUSE `0x40005D04` | none | fixed 37-register dump (`0x11C1xxxx`), unmasked, sent to host | info-leak only (SBC state, device-info words, oplus-cert fields); **no key material** | no |
| CMD:READ-REGISTER | **does not exist on 2710** | — | — | — |
| CMD:WRITE-REGISTER | **does not exist on 2710** | — | — | — |

The hypothesized "WRITE-REGISTER ungated → forge auth flag" chain from the 200EX01 map is
**not needed on 2710**: WRITE-EFUSE itself is the arbitrary-write primitive, and the
`g_oplus_auth_status ← 5` forge was demonstrated through it.

## 1. Command table (task 1)

Registrar `0x400083DC(name, group, handler)`; registration site `0x40001A78` (plus a second
block at `0x40001D24`). Full extract (movw/movt pairs, `bl 0x400083DC`), 25 entries:

```
0x40001A84  movw r0,#0x161f  ; "CMD:WRITE-EFUSE"
0x40001A88  movw r2,#0x5c20
0x40001A9C  bl  0x400083DC         → handler 0x40005C20
0x40001AA0  movw r0,#0x162f  ; "CMD:READ-EFUSE"
0x40001AA4  movw r2,#0x5d04
0x40001AB4  bl  0x400083DC         → handler 0x40005D04
```

Both EFUSE commands are registered **unconditionally at the top of the block**, before the
`[0x40054C88]∈{3,4}` oplus-permission gate at `0x40001AD0` that conditionally registers
WRITE-PARTITION/WRITE-FLASH/WRITE-PARTITIONS. A whole-image scan for `bl 0x400083DC`
finds exactly these 25 call sites — **there is no READ-REGISTER/WRITE-REGISTER anywhere**,
and the strings `REGISTER`, `SET-RSC` are absent from the blob (200EX01 registers
CMD:READ-REGISTER→0x40006EEC / CMD:WRITE-REGISTER→0x4000700C; on 2710 those handlers and
strings are gone).

Trigger chain for the `0x40001A78` block: `CMD:SECURITY-SET-FLASH-POLICY` (0x40006B8C)
calls it at `0x40006D1C` after its policy-file verification; the `0x40001D24` block is
called from bootstrap2 (`0x40000F40`, right after the `***10.dagent_register_commands.`
log). So the EFUSE commands become dispatchable in the same session that runs
SECURITY-SET-FLASH-POLICY — the same gate every other CMD:\* command sits behind. **No
additional per-command check exists inside either EFUSE handler** (verified by full
disassembly + emulation).

## 2. WRITE-EFUSE call tree (task 2)

```
CMD:WRITE-EFUSE 0x40005C20 (ARM)
├─ 0x40008134                     session scratch alloc (malloc 0x1000, global 0x40060A60)
├─ 0x4000CFEC(xml,0,0)            mxml parse of the packet
│   fail → 0x400081AC([0x40054924]) → 0xC0010001
├─ 0x400020AC(node,"da/arg/source_file")   ← the ONLY XML argument
│   missing → 0xC0010001
├─ 0x4002AFD8(conn, name, &len, &buf, "efuse")   fetch file from host, category "efuse"
└─ 0x40007EA8(buf, len)           dev_efuse_write wrapper
    ├─ 0x40007EC4  cmp r5,#0x200 / bne → 0xC0030007   *** the ONLY input validation ***
    ├─ 0x40031A18 (Thumb)       blow engine: parses the 512-B PAYLOAD AS XML
    │   ├─ find "debug" (0x4000ED20) → attr "lock_voltage" (0x40032C26)
    │   ├─ find "write" → attrs "fsource","vcore" (×1000, PMIC stubs)
    │   ├─ find "verify" → count+walk "vcore" children (0x40032C44/0x4000E924)
    │   ├─ find "read"  → attrs "fsource","vcore" (read-back voltages)
    │   ├─ find "extra" → count+walk "option" children:
    │   │     addr  = strtol(attr "address")   (0x4000CD2C → 0x4000AC20)
    │   │     data  = strtol(node text)        (0x4000E924 → 0x4000AC20)
    │   │     blow_list[i] = {addr, data}      ← NO validation of addr whatsoever
    │   ├─ [CORRECTION] the XML path NEVER reaches the binary-image check chain
    │   │   (img magic/hash 0x400321A8, revert checks, ackey/sbc/custk consistency
    │   │   0x400326F4..0x40032914, SBC guard 0x40032DC4, battery check). Those run
    │   │   only on the binary "ulpotrec"-image branch (XML parse failed).
    │   ├─ 0x400318EA(0): [0x11C10008] ← 0x6B32970A     (BPKEY unlock)
    │   ├─ loop 0x40031DEA: for each blow_list entry: 0x4003184A(addr, data)
    │   ├─ loop 0x40031E8A: read back each addr, compare to data (read oracle)
    │   ├─ 0x400318EA(1): [0x11C10008] ← 0             (BPKEY re-lock)
    │   └─ 0x4003189E: [0x11C10000] |= 4, wait bit0    (reinit)
    └─ 0x4000AC20 = strtol (0x/dec/neg accepted)
```

Raw writer `0x4003184A(addr, data)` (Thumb) — the primitive:

```
0x40031856  movw ip,#0x0000 ; movt ip,#0x11C1
0x4003185A  ldr.w r2,[ip] ; lsls r2,r2,#30 ; bpl …     ; poll controller ready, timeout 0x1000
0x4003186C  str r1,[r0]                                ; *** arbitrary 32-bit store ***
0x40031872  ldr.w r1,[ip] …                            ; poll done again
```

No range check, no whitelist, no auth query anywhere between XML and `str`.

## 3. READ-EFUSE call tree

```
CMD:READ-EFUSE 0x40005D04 (ARM)
├─ parse xml; get "da/arg/target_file"
├─ malloc 0x5000 (0x4000A390), memset
├─ 0x40007F58(buf, 0x5000)  (ARM)
│   └─ 0x40031964 (Thumb) dev_efuse_read:
│       memset 0x4006EFD4 (128B scratch), header "==read the blown efuse list==\n"
│       loop 37× over fixed table 0x400571F8 (stride 0x18):
│           r0 = entry[0] = raw controller register; r2 = [r0]   ← direct ldr, NO mask
│           snprintf "idx[0x%x] = 0x%x\n" (0x40050041)
└─ 0x4002B49C(conn, target_file, buf, len+1, "efuse")   send dump to host
```

The 37 dumped registers (from the table at 0x400571F8, verified dynamically with seeded
values): `0x11C10070-7C, 0x11C10090-AC, 0x11C10030/38 (mask 0xFFFF), 0x11C10510-24,
0x11C10850-5C, 0x11C10830, 0x11C1080C, 0x11C10020 (0x1417), 0x11C10060 (0x48037F),
0x11C104A0 (2), 0x11C104C4, 0x11C104C8, 0x11C10808 (0x8000), 0x11C104A4 (8),
0x11C104C0 (1), 0x11C104CC (0x1FF), 0x11C10068 (0x1F), 0x11C10028 (6)`.
Read-back is the plain register value — the entry masks are used by the blow logic, **not**
applied in `dev_efuse_read` (proved: all-ones seed dumps `0xffffffff` for every idx).

Key-material check: the DA's own word→register table at `0x400540F4` (72 entries, word-id
API `0x40031770`) maps AC_KEY/CUSTK/HRK-family words to `0x11C107A0-CC` and `0x11C106A0-A4`
/ `0x11C10140-4C` (naming per mtkclient `zeroization()`: idx 0x10-0x13 = AC_KEY,
0x14-0x17+0x1A = CUSTK, 0x08-0x0F = HRK — `mtkclient/Library/DA/mtk_da_handler.py:1159`).
**None of those registers appear in the 37-entry dump list** → READ-EFUSE leaks no
DAA/RPMB/hw-secret material. It does expose the SBC word (`0x11C10060`, incl. the sbc_en
bit) and the device-info word block `0x11C10090-AC` (word-ids 0x37-0x3E, same family as the
200EX01 whitelist) — same info class the 200EX01 whitelist already allowed, unmasked.
mtkclient independently pins `efuse_addr = 0x11C10000` for MT6789/hwcode 0x1208
(`mtkclient/config/brom_config.py:1957`) [CORRECTION: the prior note's "UNISOC controller"
guess is wrong; this is the MTK MT6789 efuse controller, and the 37-entry table matches
mtkclient's `internal_fuses` family for this efuse block].

## 4. Fuzz results (task 5)

Corpus + classes in `/tmp/opencode/efuse2710/fuzz_efuse.py`; log `fuzz_output.txt` (exit 0).
Layers: L1 = payload entry `0x40007EA8(data,len)`; L2 = dump entry `0x40007F58`; L3/L4 =
full registered handlers with host-file fetch/send/reply stubbed. Device model: the efuse
controller window 0x11C10000-0x11C12000 is dict-backed (writes recorded + stored, reads
return stored value; ctrl/status reg 0x11C10000 modeled idle); PMIC/battery/delay calls
stubbed at entry; every write in the whole address space is recorded with (addr, val, pc).

### L1 — WRITE-EFUSE payload (38 cases)

| EFUSE-WRITE | 9 | wrote real efuse-controller data registers (target taken from XML) |

| ERR | 9 | `0xC0030007` — length gate rejects len≠0x200 |

Required XML shape (document-order, discovered by instrumenting the mxml walkers):
`<debug lock_voltage?="…"><write fsource="…" vcore="…"><verify><vcore>N</vcore></verify>
<read fsource="…" vcore="…"/><extra><option address="0x…">DEC</option>…</extra></write></debug>`
— root element name is irrelevant (`<efuse>`, `<da>`, `<a/>` all work); `read`/`verify` are
optional; **only `<write>` + `<extra>/<option>` are needed to fire the raw write.**

### READ-REGISTER / WRITE-REGISTER corpus

Not applicable — the commands do not exist on this build (§1). For the record, on 200EX01

## 5. Classification of reachable write targets (task 3)

* **(b) NO AUTH — DANGEROUS.** The `<extra>/<option>` debug path performs raw
  `*(u32*)addr = data` with the address taken verbatim from host XML:
  * every efuse-controller register, incl. the security word `0x11C10060`
    (sbc_en = bit1, daa_en, sla_en, jtag_dis, Enable_SW_JTAG_CON, Disable_Rom_Cmd per the
    secure-setting dump `0x40032DC4`-region decode; cross-checked with `re-tee-efuse.md`:
    word 0x1F bit1 = SBC) and the lock words (`0x11C10020` mask 0x1417 = sec_ctrl_lock /
    sbc_pubk_hash_lock bits). **Efuse bits are 0→1 only: blowing sbc_en/daa_en/lock bits on
    a factory-fresh unit is irreversible → device-bricking class.**
  * arbitrary DA RAM (`0x40054C88` g_oplus_auth_status demonstrated) → all oplus policy
    gates that read the auth level (`0x4002CDB0` "oplus_single_mode" special case for
    auth==5, "Security deny for [%s]" paths) can be forged.
  * arbitrary SoC MMIO (watchdog `0x10007000` per mtkclient MT6789 chipconfig was written
    in emu) and the DA's own code segment.
* **(a) auth/content-gated:** only the *binary* `ulpotrec`-image branch (XML parse must
  fail) runs the img-SHA256 check (`0x400321A8`), the revert/ECC/ackey/sbc/custk chain
  (`0x400326F4…0x40032914`), the SBC guard `0x40032DC4` and the battery check. That branch
  is the OEM flash-tool flow and is NOT the path a hostile client needs.
* **(c) dead/stubbed:** none — nothing in the write path is stubbed out on this build.

## 6. Exploit chain verdict (task 6)

1. Host completes the session auth it needs for any flash session (SECURITY-SET-FLASH-POLICY
   registers the CMD table — same precondition as WRITE-PARTITION; no extra check afterwards).
2. `CMD:WRITE-EFUSE` with a 512-byte XML containing
   `<write><extra><option address="0x40054C88">5</option></extra></write>` →
   **g_oplus_auth_status = 5**, rc=0. No efuse side effect, fully reversible (RAM write).
3. Same command, second option `<option address="0x11C10060">…</option>` → blows the
   security-control efuse word (irreversible).
4. Or point `address` at any other SoC register (RGU, seccfg-adjacent, PMIC) — the store is
   unvalidated.

**Bottom line: efuse path = EXPLOITABLE and BRICKING-DANGEROUS.**
* WRITE-EFUSE: ungated arbitrary 32-bit write (write-what-where), proven in emulation at
  three layers (payload entry, blow engine, full registered handler), including a real
  efuse word and the oplus auth global. The only validation in the entire path is
  `cmp len,#0x200`.
* READ-EFUSE: benign (fixed 37-register dump, no key material, unmasked but non-secret).
* READ/WRITE-REGISTER: absent from this build — the 200EX01 gate question is moot here.
* The debug-XML write path also bypasses every guard the "official" image path has
  (img hash, revert/ECC/ackey/custk consistency, SBC-engaged guard `0x40032DC4`, battery
  check) — [CORRECTION] to the prior note, which attributed those guards to the write path
  generally.

Mitigation note for mtkclient: do not implement `CMD:WRITE-EFUSE` against this DA family;
if read-only efuse info is needed, `CMD:READ-EFUSE` (fixed dump) is safe to parse but leaks
SBC state — treat as info, not as an unlock primitive.
