## 1. Corrections to the briefing (measured, not inherited)

1. `97e49b50581b063d…` is **not** the sha256 of the 2710 preloader — it is the
   sha256 of the **0x100-byte key block** `97e49b50581b063d78cac4548ed124d0…2df134`.
   The preloader itself is `677d1febbbf10e4f…`. The two numbers got conflated.
2. `0x25E1EC` / `0x25E2EC` are **VAs**, not file offsets. File offsets are
   `0x5D2DC` (A) and `0x5D4DC` (B); and B's base is different (0x200F00), so the
   "+0x100 shift" is not a byte shift of the same image region.
3. The "byte-identical 0x100-byte key block" is real, but it is the **old** key
   **K1**, and its placement is:
   * A: `0x25E0EC` **and** `0x25E1EC` — the same modulus stored twice (0x100-periodic);
   * B: `0x25E2DC` **only**; B's DA slot is the **new** key K2 at `0x25E3DC`.
   So "the 2710 preloader carries our key" is true but misleading: that copy is
   wired to the **seccfg / BR-cmd** path (`0x2378AC`, strings
   `[%s] seccfg part not found`, `[%s] BR cmd is disabled`), **not** to DAA.
   The "candidate blocks at 0x25E3DC/0x25E3EC" are the same key seen at two
   alignments: `0x25E3DC` is the slot start, `0x25E3EC` is 0x10 bytes into it.

## 2. Q1 — the RSA check: scheme, message, key

### 2.1 Scheme = RSASSA-PSS(SHA-256, sLen=32), *not* PKCS#1 v1.5

PSS verifier, A `0x24138C..0x2415E6` (called from the DA verify via
`0x241682(digest,decrypted,&ok,mode)`), decisive instructions:

```
002414aa  add.w  r0, r6, sl          ; r6 = emLen, sl = decrypted buffer
002414b0  ldrb   r0, [r0, #-0x1]     ; EM[emLen-1]
002414b4  cmp    r0, #0xbc           ; PSS: last byte must be 0xBC
002414b6  bne    #0x2414f2           ; -> error -8
002414b8  sub.w  sb, r8, #0x21       ; DB len = emLen-0x21 (hLen=0x20)
...
00241510  ldr    r1, [sp, #4]        ; H
00241512  movs   r0, #0xff
00241514  lsr.w  ip, r0, sl          ; top-bit mask (emBits = modBits-1)
...
00241520  ldrb   r3, [r1], #1        ; DB ^= MGF1(H)   (0x2412CE = MGF1)
0024152a  eor.w  r0, r0, r3
0024152e  strb   r0, [r2], #1
...
0024157e  cmp    r1, #1             ; first non-zero byte of DB must be 0x01
00241580  bne    #0x2415e8
```

then SHA-256 re-computation over `0x00*8 || mHash || salt` (`0x241708`/`0x241724`/
`0x2417E4`) and `memcmp` (`0x238620`). The 2710 build carries the same scheme with
different codegen: tail check `B 0x2415E0 cmp r0,#0xbc`, MGF1 `0x2413FA`,
DB separator `B 0x2416AA cmp r1,#1`, digest `memcmp 0x23874C` at `0x241704`.
Empirically confirmed: every accepted pair below yields **salt = 32** and
`H' == H`. A PKCS#1 v1.5 probe over 17 543 candidate moduli produced **zero**
hits — the scheme is PSS, which is why a v1.5 test "fails".

### 2.2 What is signed

The preloader takes the **last `sig_len` bytes of the received DA image** as the
signature and PSS-verifies the preceding `da_len − sig_len` bytes:

```
A 0x208666  cmp   sl, r5            ; sl = da_len, r5 = sig_len
A 0x208668  bls   #0x208694         ; da_len <= sig_len -> "da_len is less than sig_len"
A 0x20866a  sub.w r1, sl, r5        ; msg_len = da_len - sig_len
A 0x20866e  mov   r0, sb            ; msg base
A 0x208670  add.w r2, sb, r1        ; sig ptr = msg base + msg_len
A 0x208674  mov   r3, r5            ; sig_len
A 0x208676  bl    #0x23780c         ; thunk: if (r3 != 0x100) return -1; -> 0x23E96A
A 0x20867a  cmp   r0, #0
A 0x20867e  movwne r0, #0x7024      ; DAA_SIG_VERIFY_FAILED
```

(B: identical at `0x208704..0x208720`, thunk `0x237938` → `0x23EA96`.)

Hard limits: `sig_len` must be **0x100** (thunk `A 0x23780C: cmp.w r3,#0x100 ;
bne -> mov r0,#-1`), and `da_len ≤ 0x100000` (`A 0x208626 cmp.w sl,#0x100000`,
else `0x1D10 DA_EXCEED_MAX_DA_BLOCKS`; B `0x208692`). Ours is 0x689FC → passes the
size limit.

Consequences, proven by the successful PSS check:

* the signed message is **`DA_BR.bin[0xBC .. sig_offset)`** — the DA1 payload
  starting at its ARM vector table (`ff ff ff ea 00 00 0f e1 …`), length
  `0x688FC`, sha256 `df2ad54612922bf71264cd8f2f879d0f40504214f1bf93ff7d745f3a97b7953e`;
* the 0xBC-byte **container header** (`MTK_DOWNLOAD_AGENT`, `MTK_DA_v6_…`,
  hwcode/subcode/hw_ver) is **outside** the signed range → the preloader cannot be
  checking those fields (and there is no reference to the container magic
  `0x22668899` anywhere in A or B — searched as raw u32 and as `movw/movt`);
* **no** version/date/anti-rollback field is covered or compared.

This matches the host side: `mtkclient/Library/DA/xflash/xflash_lib.py:963-979`
seeks to `region[1].m_buf` (=0xBC) and sends `m_len` (=0x689FC) bytes, i.e. the
DA1 sub-image including the 0x100 trailer — exactly the byte range we verified.

### 2.3 Which key, and the proof

Key install path: `key_setup(ptr,len)` copies the blob into RAM key buffers by
declared size (`0x100→0x2F96A8`, `0x180→0x2F97A8`, `0x200→0x2F9928`), sets the
"key ready" flag and stores the pointer:

```
A 0x23E8F8  cmp.w r1,#0x100 ; movw r4,#0x96a8 ; movt r4,#0x2f ; bl 0x23860c (memcpy)
A 0x23E944  movw r0,#0x9b28 ; movs r1,#1 ; strb r1,[r0]     ; *(0x2F9B28)=1
A 0x23E950  movw r0,#0x9b38 ; str r4,[r0]                   ; *(0x2F9B38)=key ptr
B 0x23EA24  (same shape; 0x100 -> 0x2F9AA8, flag 0x2F9F28, ptr 0x2F9F38)
```

The only callers, and therefore the whole DA-key story:

| build | wrapper (loads key) | called from | key blob | content |
|---|---|---|---|---|
| A | `0x237820`: `ldr r0,[pc,#0x18]` → `0x25E1EC`; `mov.w r1,#0x100`; `bl 0x23E8F8` | **`0x208620`** (single call site, inside `usbdl_verify_da`) | `0x25E1EC..0x25E2EC` | **K1** |
| A | `0x237780` tail of the seccfg/BR-cmd function | seccfg path only | `0x25E0EC..0x25E1EC` | K1 (duplicate) |
| B | `0x23794C`: `ldr r0,[pc,#0x18]` → `0x25E3DC`; `mov.w r1,#0x100`; `bl 0x23EA24` | **`0x20868C`** (single call site, inside `usbdl_verify_da`) | `0x25E3DC..0x25E4DC` | **K2** |
| B | `0x2378AC` tail of the seccfg/BR-cmd function | seccfg path only | `0x25E2DC..0x25E3DC` | K1 (stale copy) |

```
A 0x20861e  b     #0x2081f4  (state loop)
A 0x208620  bl    #0x237820          ; install K1
A 0x208624  cbnz  r0, #0x208632      ; install failed -> ...
A 0x208632  movw  r0, #0x7024

B 0x20868c  bl    #0x23794c          ; install K2
B 0x208690  cbnz  r0, #0x2086d4      ; -> movw r0,#0x7024
```

Moduli (big-endian, RSA-2048, e=65537):

* **K1** `sha256 97e49b50581b063d78cac4548ed124d096dc1a6d419bb3bc6664124e002df134`
  starts `aa c9 c1 f3 72 d4 dc 9e b6 e4 62 e3 2f cd 57 6b …`, ends `… fe 60 5a e7`.
* **K2** `sha256 8b953efd5ce8a86190fd28bea2c4034a9fd0c17e973e9ac61993aa64031baced`
  starts `af 10 2e 73 89 d1 a2 4d ff 4a 19 e2 41 71 6d 73 …`, ends `… 49 72 95`.
* K1 ≠ K2, and `K1 == B[0x25E2DC] == A[0x25E0EC] == A[0x25E1EC]`.

### 2.4 Verification results (PSS-256, salt auto-detected)

| key | signature | message | result |
|---|---|---|---|
| K1 | A DA1 trailer `0x689B8` | `A[0xBC..0x689B8)` | **PASS**, salt 32 |
| K1 | A DA2 trailer `0xBF980` | `A[0x68AB8..0xBF980)` | **PASS**, salt 32 |
| K2 | B DA1 trailer `0x693E0` | `B[0xBC..0x693E0)` | **PASS**, salt 32 |
| K2 | B DA2 trailer `0xC0AF0` | `B[0x694E0..0xC0AF0)` | **PASS**, salt 32 |
| **K2** | **A DA1 trailer** | our DA1, all candidate ranges | **FAIL — `m[0xFF]=0x3C ≠ 0xBC`** |
| K1 | B DA1 trailer | his DA1 | FAIL — `m[0xFF]=0x62` |
| K1 | B DA2 trailer | his DA2 | FAIL — `m[0xFF]=0x2E` |
| K2 | A DA2 trailer | our DA2 | FAIL — `m[0xFF]=0x7C` |

So the mapping is strictly bijective: **200EX01 DAs ↔ K1, 2710 DAs ↔ K2**. Both
AllInOne containers in both packages ship **zeroed** trailers (`sig_zero=True` on
all 3 entries each) — the signed copies are the `DA_BR.bin` ones only, which is
consistent with `re-preloader-daa-lk.md` §Q1.

Note the products' own naming: A's header says `MTK_DA_v6_2024-09-02 22:21:09`,
B's says `MTK_DA_v6_2025-12-09 15:56:46 DA_05 KEY_02`, and B's preloader contains
the string `OPLUS_DEFINE_20240326_DA_KEY_VER_02` (VA 0x24C19F) — i.e. the vendor
itself calls this key set "KEY_02".

## 3. Q2 — SBC (SoC binding): what the header fields are worth here

| field (container offset) | A | B | compared by preloader? |
|---|---|---|---|
| `0x6C` u32 `0x1208dada` (hwcode 0x1208 / "dada" tag) | same | same | **no** |
| `0x70` u16 `0x8A00` (subcode) | same | same | **no** |
| `0x72` u16 `0xCA00` (hw_ver) | same | same | **no** |
| `0x64` magic `0x22668899`, `0x68` `da_ver=1` | same | same | **no** (magic absent from both binaries) |
| `0x80+i*0x14` entry table `{off,size,load,sig_off,sig_len}` | `bc000000 fc890600 00002000 b8890600 00010000` ×2 + `b88a0600 c86f0500 00000040 80f90b00 00010000` | `bc000000 24940600 00002000 e0930600 00010000` ×2 + `e0940600 10770500 00000040 f00a0c00 00010000` | only by the **host tool** (`mtkclient` reads `region[1]`); the preloader never receives this header, so it cannot read the table — it takes `sig_len` from its own state (`[0x25F160]`/`[0x25F350]` = 0x100) |

Proof that the header is outside the authenticated data (§2.2): the PSS passes
over exactly `[0xBC, sig_off)`. Byte-identical SBC fields therefore change
nothing; the effective binding is the modulus (K1 vs K2). If a DA signed with the
*right* platform key were sent, the header's hwcode would still never be looked
at by this stage — SoC/socid checks (`check_socid`, `[EFUSE] sbc_pub_key_hash`,
`[%s] cert chain vfy fail`) exist only in the **boot-image** path
(`partition.c`, B `0x2310F0..` / cert-chain `0x23Exxx`), not in `usbdl_vfy_da`.

Negative control for the "magic absent" claim: the only 0x8899 halfword in either
image is `va 0x23CE1A` (A) / `0x23CF46` (B), which is the middle of the encoding
`41 f0 20 01` = `movw r1,#0x2001`, and the only 0x2266 sits elsewhere
(`0x22B744`/`0x22B810`); there is no `movw/movt` pair and no pool word for
`0x22668899`.

## 4. Q3 — DAA / SLA: what is enforced and by what material

### 4.1 The gate that can disable verification (and why it does not save us)

```
A 0x2084ac  movs r0, #1
A 0x2084ae  bl   #0x241046        ; "is DA verification enabled?"  (B: 0x241172 @ 0x2084ba)
A 0x2084b2  cmp  r0, #0
A 0x2084b4  bne.w #0x208620       ; enabled -> PSS path
A 0x2084b8  ldr  r0, = 0x2475B1 "usbdl_vfy_da:disabled"
A 0x2084c0  b    #0x2086a4        ; r0=0 -> falls through to 0x2086CC: *(0x2F3158)=1
```

`0x241046` (B `0x241172`) is a sec-policy read:

```
A 0x24104a  movw r0,#0xb288 ; movt r0,#0x2f ; ldr r0,[r0]   ; *(0x2FB288)
A 0x241056  cmp  r2, #0x22  ; beq -> bl 0x243190; return (result == 1)  ; secure-boot state
A 0x24105a  cmp  r2, #0x11  ; beq -> return 1
A 0x24105e  cbnz r2, #0x241072                                     ; else assert
A 0x241060  movs r0, #0     ; sec-mode 0  -> verification DISABLED
```

i.e. on a locked/SBC-blown retail unit the DAA path is live; the "disabled" branch
is the no-secure-boot factory case. This is *not* a bypass we control.

### 4.2 The DAA flag and the jump gate

```
A 0x2086cc  ldr  r1,[pc,#0x24]   ; = 0x2F3158
A 0x2086ce  movs r0,#1
A 0x2086d0  strb r0,[r1]         ; *(0x2F3158) = 1   (DAA verified)   [B: 0x20876a]

A 0x208564  ldr  r0,[pc,#0x18c]  ; = 0x2F3158        (usbdl_jump_da)  [B: 0x208570]
A 0x208566  ldrb r6,[r0]
A 0x208568  subs r4,r6,#1
A 0x20856a  it   ne
A 0x20856c  movwne r4,#0x7024    ; DAA_SIG_VERIFY_FAILED
A 0x208576  cmp  r6,#1
A 0x208578  beq  #0x208590       ; only if verified
A 0x20857a  ldr  r0,= 0x247607 "%s usbdl_jump_da: %x"   ; then assert at download.c:0x256
```

`*(0x2F3158)` is set **only** in the success tail of `usbdl_verify_da` (the only
two xrefs to that global are `0x208564` and `0x2086CC`). So a failed PSS ⇒ jump
refused ⇒ `0x7024`.

### 4.3 Device-specific? No.

In the whole DA path (`0x2081F4..0x2086D8`) there is **no** certificate parsing, no
`socid`, no efuse/SBC hash, no per-unit secret: one built-in 2048-bit modulus and
PSS. DAA is a *platform* (vendor) signature check, identical on every unit of the
product generation. `SLA` appears only as an efuse *dump/blow* string
(`[EFUSE] sla_en = %s`, A 0x258BE3 / B 0x258DD3) with no consumer in the DA path;
the per-device `g_oplus_auth_status` gate that the DA2 layer uses (see
`re-oplus-auth-paths.md`, `re-da2-2710-audit-2026-10-25.md`) lives inside the DA,
not in the preloader — and we never get there, because the preloader refuses to
jump.

Risk note (not an exploit path, just the cost of trying): a rejected DA goes
`0x7024` → B `0x208742` / A `0x2086A4` → `"clean invalid da"` →
`memset(buffer,0,da_len)` → `assert(download.c:0x256 A / 0x259 B)`, i.e. the
preloader enters its `%s USB Disconnect and Enter Dead Loop...` assert instead of
returning to the USB loop. Nothing is written to flash, but the session is wedged
until power-cycle.

## 5. Q4 — anti-rollback / version

**In the DA path: none.** No version compare, no date compare, no `da_ver` field
reference, no anti-rollback counter read anywhere between the USB receive and the
jump; the only numeric checks are `da_len ≤ 0x100000` and `sig_len == 0x100`.

**A separate OPLUS mechanism exists in B only** (absent from A — the strings
`[oplus da]…` and `OPLUS_DEFINE_20240326_DA_KEY_VER_02` do not exist in A at all):

```
B 0x230C5C  movs r0,#0 ; str r0,[sp,#4] ; movs r0,#7
B 0x230C68  bl   #0x2426cc              ; get "version item 7" -> [sp+4]
B 0x230C72  ldr  r0,= 0x24ED3E "[oplus da]get da version error. ret=%d da_ver=%d"
B 0x230C76  ldr  r0,= 0x24ED70 "[oplus da]get da version ok. ret=%d da_ver=%d"
B 0x230C80  cmp  r0, #5
B 0x230C82  beq  #0x230cac              ; already 5 -> nothing to do
B 0x230C84  ldr  r0,= 0x24ED9F "[oplus da]write da version"
B 0x230C8A  movs r0,#7 ; movs r1,#5
B 0x230C8E  bl   #0x242842              ; set item 7 = 5
B 0x230C9C  ... re-read, print ok/error
```

`0x2426CC(7,&v)` / `0x242842(7,5)` are the seclib version-table getter/setter
(strings around `0x257783`: `[ver]ver:(verk,verc,otp)=(%d, %d, %d)`, implemented
on top of the storage helpers `0x244D00` (read) / `0x244DC0` (write); whether that
backing store is RGU, OTP or a partition is **not** proven here), i.e. **B records
a DA-version floor of 5** (consistent with the DA banner `… DA_05 KEY_02` and the
string `OPLUS_DEFINE_20240326_DA_KEY_VER_02`).

*What this floor is compared against, and where, is* **UNKNOWN** — its only call
site is the sec-lib init (`0x228A1C`), and nothing in `usbdl_verify_da` reads
items 0..7. Treat "the 2710 preloader would additionally reject a `DA_04` build by
version" as **unproven**; the signature check already settles the question.

Cheapest experiment to close it (described, **not run**): power on the unit with a
UART/USB log capture — the preloader prints `[oplus da]get da version ok. ret=%d
da_ver=%d` during sec-lib init, which names the live value and whether the write
happened. One boot, one log line; no host tool and no flash access needed.

## 7. What would have to be true for the swap to work

1. A DA1 whose PSS trailer verifies under **K2** with message `DA1 payload`.
   Signing that requires the K2 private key (MTK/OPLUS) — not available.
2. Or a `da_len/sig_len`/`0x7024` bypass inside the preloader — none found: single
   call site, single key, `cmp r0,#0` on the install path, `0xBC` check first, no
   fallback attempt with the other slot, no "unsigned DA" mode (that is BROM, not
   this stage).
3. Or `*(0x2F3158)` forged before `jump_da` — RAM-only, requires code execution in
   the preloader (i.e. a preloader/BROM exploit), which is the mtkclient
   BROM-exploit route, not a DA swap.

Conversely, the 2710's own K2-signed `DA_BR.bin` will be rejected the same way by
our 200EX01 preloader (measured above: `m[0xFF]=0x62` under K1).

def mgf1(seed,n):
    o=b''; c=0
    while len(o)<n: o+=hashlib.sha256(seed+c.to_bytes(4,'big')).digest(); c+=1
    return o[:n]

def pss(n,sig,msg):
    k=(n.bit_length()+7)//8
    m=pow(int.from_bytes(sig,'big'),65537,n).to_bytes(k,'big')
    if m[-1]!=0xBC: return False, 'tail 0x%02X'%m[-1]
    db=bytearray(x^y for x,y in zip(m[:k-33], mgf1(m[k-33:k-1],k-33)))
    i=db.find(b'\x01',1); salt=bytes(db[i+1:])
    return hashlib.sha256(b'\0'*8+hashlib.sha256(msg).digest()+salt).digest()==m[k-33:k-1], len(salt)

DA = open('docs/notes/rmx3630-da2/DA_BR.bin','rb').read()

## 11. Consequence for the 2710 / PR #414 discussion

`re-da1-hash-patch-audit.md` and the HeapBait work target the **DA1 that our
200EX01 preloader accepts**. On the 2710 unit that DA1 cannot even be loaded: the
platform rotated the DAA key (K1 → K2, `KEY_02`). Any 2710-side DA1 work must
therefore start from `DA_BR.bin` of the 2710 package (`sha 2e15a832…`,
`… DA_05 KEY_02`), whose signature verifies under K2 — i.e. exactly the build that
`da1_static_audit.py` already classifies as PATCHED (no `CMD:DEBUG:DRAM-REPAIR`,
tripwire present). The key rotation and the DA1 hardening are independent, and
both block the 200EX01 → 2710 transplant.
