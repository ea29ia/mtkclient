# RE: WRITE-PARTITION (0x40002034) — куда уходят данные и почему misc пострадал по offset 0x80C/0x818

Бинарник: `/home/musin/firmware/extracted/IMAGES/da2_oplus.bin` (356296 B), ARM32.
**Маппинг подтверждён (proven):** file offset 0 == VA 0x40000000. Проверка: file offset 0x2034
дизассемблируется как `push {r4-r8,sb,sl,fp,lr}; add fp,sp,#0x1c; sub sp,#0x32c` — корректный
пролог обработчика на VA 0x40002034. Инструмент: objdump/r2 недоступен полностью — использован
capstone (ARM/Thumb), поэтому адреса/инструкции ниже — точные байты из файла.

Контекст: смежные заметки `re-write-chain.md`, `re-writeflash-scrubber.md`, `re-postwrite-hang.md`.

## TL;DR

1. **У WRITE-PARTITION вообще нет XML-узла offset.** Адрес записи = начало партиции, взятое
   из таблицы партиций DA (`0x40012e9c` → parse в 0x58-структуру, поле +0x50 = старт).
   Единственный способ задать подобласть — узлы `<space_list><space offset=... length=.../>`
   внутри `<source_file>` (proven). mtkclient их не шлёт → область = вся партиция от 0.
2. **Числовой обмен внутри data-фазы: DA сам диктует строку `"0x0"` и парсит ответ хоста
   `OK@<hex>` через ascii-hex→u64 (`0x4000aef4`).** mtkclient шлёт `ack_value(total)=OK@0x800`
   первым и `ack_value(0)=OK@0x0` на каждый пакет — значения не совпадают с тем, что DA
   ожидает как «offset/длина следующего куска». Это единственное место, где хост управляет
   числом, и это главный подозреваемый в «съехавшей» записи (inferred, см. §4).
3. Факт-картина на flash (0x0–0x7FF нули как были; изменились только 8 байт внутри BCAB на
   0x80C/0x818; 0x8000 не тронуто) **не соответствует** ни «наши 0x800 байт легли на +0x800»
   (тогда BCAB был бы затёрт нулями), ни «полный erase партиции» (тогда BCAB исчез бы).
   Наиболее согласованная версия: **data-фаза не закоммитила наши байты вообще**
   (dispatcher программы `0x4002aac0` молча пропускает запись, если глобальный page-size
   `[0x40054330+0x10]` не сконфигурирован для этого пути — proven-инструкция, смысл inferred),
   а 8 изменённых байт — побочный эффект erase-фазы/OPLUS-книгучёта в BCAB (inferred, низкая
   уверенность, см. §5).

## 2. Как вычисляется адрес записи (механизм)

**XML-парсер (0x40002034 → 0x400024xx), proven:**

- `0x40002070 bl 0x4000d0bc` — поиск `da/arg/partition`; fail → `0x400084a4` err (0x4000211c).
- `0x40002088/a4` — поиск `da/arg/source_file`; fail → err.
- `0x400020c0` — поиск `da/arg/pre_erase` → r8. `0x400021e8`: `0x4000b5e0(node,"YES",4)`
  → pre_erase==YES ⇒ пропустить erase-путь (bne 0x40002218).
- Нет узла ⇒ `0x40002204`: имя!="PRELOADER" (`0x4002c6cc`==0 @0x40002214) ⇒ `0x400022a8`:
  лог `Erase [misc] At[0x%llx] Len[0x%llx]` (значения из 0x58-структуры, т.е. **старт и размер
  всей партиции**) и `blx [0x40054374+8]` (0x4002eca4) @0x40002308.
- Опциональный `<space_list>`: `0x40002350 bl 0x4000edf0` → на каждый `<space>`:
  `0x40002370 bl 0x4000cdfc("offset")`, `0x40002384 bl 0x4000cdfc("length")`,
  оба через `0x4000aef4` в u64, кладутся в массив с шагом 0x10 (`0x40002394 strd [r6]`,
  `0x400023a8 strd [r6,#8]`, `0x400023c4 add r6,r6,#0x10`). Пустой offset/length при отсутствии
  узлов: массив пуст (sb=0), `0x4002d970` собирает регион по умолчанию = **вся партиция от её
  старта** (0x400023d4: `[sp+0x28/0x2c]` из `[sp+0xc]` = region+0x50 → старт; `0x4002408`
  сохраняет указатель региона в fp-0x80).

**Data-фаза (0x4003010c), proven:**

- `0x4003014c bl 0x4003053c(sp+0xc)`: DA шлёт `"0x0"`, читает ответ, требует "OK".
- `0x4003016c bl 0x4000aef4([sp+0xc])` — число из ответа → u64.
- `0x4003017c strd r0,r1,[slot_0x4006E7CC+0x10]`; `0x40030180-90`: сравнение с
  `[slot+0x20]→[+0x50]` (размер партиции), при переполнении —
  `"Data size bigger than partition max size."` (0x40043ac9).
- Приём пакета: `0x40030388-98`: `r0 = [slot+8] + sl` (RAM bounce-буфер + накопленный
  сдвиг), `blx [0x40054320]` (0x4002a934, USB recv; длина пакета возвращается в [sp+0x10]).
- Advance: `0x40030418-28`: `[slot+0x10] += recv_len` (r7=[sp+0x10]); выход из цикла когда
  `sl >= [sp+4]` (= `[0x40067A08+0x1c]`).
- **Вывод (proven по инструкциям, семантика inferred):** адрес на flash для записи определяется
  базой из открытого региона (`0x4002f5f8`, слот+0x10 инициализируется open'ом) и
  накапливается по факту принятых байт; XML-узла offset нет; парсированное из ответа число
  используется как проверка объёма. Т.е. **при штатном обмене данные обязаны лечь с offset 0
  партиции последовательно.**

## 3. Что шлёт mtkclient и где расходится с DA

`xml_cmd.py::cmd_write_partition` (строка 442): шлёт только `<partition>` +
`<source_file>MEM://0x0:0x800` — **поля offset нет by design** (для WRITE-FLASH оно есть,
строка 456, но это другой хендлер). `pre_erase` не шлётся ⇒ срабатывает erase-путь (см. §2).

Протокол data-фазы у mtkclient (`xml_lib.py::upload`, строка 602):
1. `ack_value(length)` → `"OK@0x800"` — consumed DA'ой в `0x4002ae28` (там проверяются только
   байты 'O','K') **или** первым обменом цикла — по таймингу.
2. Далее на каждый пакет `ack_value(0)` → `"OK@0x0"`, потом сырой пакет.
3. `raw=True` → финальный `ack()`.

DA же в каждом обмене цикла (0x4003053c → 0x4003016c/0x40030344) **парсит число из строки
ответа**. Числа mtkclient (0x800 затем нули) либо трактуются как объём/offset куска, либо
ломают выходное условие цикла — в любом случае семантика ack'ов mtkclient не совпадает с
ожиданиями этого DA2 (proven: парсинг существует; точная семантика — inferred).

## 4. Почему байты легли не туда (реконструкция)

Факты: `0x0-0x7FF` нули (как и до записи), `0x80C`: `9f 00 0e 00` → `ff 00 7f 00`,
`0x818`: изменились 4 байта (timestamp-подобные), `0x8000` не изменён, BCAB-магнитуда
`_a\0\0` + `BCAB` @0x800, версия `0102` — цела. В DA **нет строки "BCAB"** (grep proven),
т.е. DA не знает про BCAB явно.

- Гипотеза A «данные легли на part+0x800» — **отпадает**: BCAB был бы перезаписан нулями
  нашего payload.
- Гипотеза B «полный erase партиции прошёл» — **отпадает**: BCAB цел.
- Гипотеза C (рабочая, inferred): **data-фаза не докатилась до program.** Цепочка:
  mtkclient `upload()` после `ack_value(0x800)` ждёт ответ `=="OK"`, а DA первым делом шлёт
  строку `"0x0"` (0x4003053c) → `resp=="0x0" != "OK"` → upload() aborts → наши байты не
  отправлены/не докоммичены; erase-фаза (без pre_erase) отработала по своему региону, но
  фактическое стирание на UFS у OPLUS-пути, судя по всему, ограничено/частично (erase
  dispatcher 0x4002eca4 берёт границы из копии 0x58-структуры; с пустым space_list и
  особенностями FTL реальный erase мог не затронуть LBA BCAB). 8 изменённых байт на 0x80C/
  0x818 при этом — либо побочный продукт erase-пути (обновление счётчика/штампа внутри BCAB
  каким-то OPLUS-хуком — в DA есть строки `[EFUSE] WARNING: by pass misc check` 0x400500af
  и OPLUS-специфика misc), либо артефакт частичного программирования 4K-сектора FTL.
  **Однозначно атрибутировать эти 8 байт коду DA в текущей сессии не удалось** — честная
  неопределённость; для точного ответа нужен UART-лог DA во время воспроизведения
  (строки `Erase [...]`/`offset=%d` печатаются при loglevel ≤ DEBUG, gate `0x40007cbc`).
- То, что 0x800 байт «данных» нигде не появилось (ни на 0, ни на 0x800), подтверждает C:
  полезная нагрузка до program-диспетчера в закоммиченном виде не дошла.

## 5. Как ПРАВИЛЬНО записать в partition offset 0 через этот DA2

1. **Контролировать erase:** слать `<pre_erase>YES</pre_erase>` (парсер proven: memcmp "YES",4
   @0x400021f4 → skip erase) — тогда erase-фаза пропускается и запись не должна трогать
   соседние данные; при необходимости erase отдельно через ERASE-PARTITION/ERASE-FLASH.
2. **Починить ack-семантику data-фазы:** DA после каждого `0x4003053c`-обмена парсит
   `OK@<hex>` (0x4000aef4). В `xml_lib.py::upload()` заменить `ack_value(0)` на ack текущей
   абсолютной позиции (`ack_value(pos)`), а первый `ack_value(length)` — оставить как ответ
   на DOWNLOAD-FILE; ответ на строку `"0x0"` от DA читать через `get_response()` до сравнения,
   а не abort'ить (сейчас `resp == "OK"` строго). Требуется живая проверка по логу DA — какие
   числа он ждёт (offset vs length); в логе `[%s] buf_chk: cur_offset_low = 0x%x`
   (0x40051748) DA печатает текущий offset — по нему видно расхождение.
3. **Альтернатива — WRITE-FLASH с явным offset** (хендлер 0x40002e60, узел `da/arg/offset`
   0x40041d99 proven; mtkclient `cmd_write_flash(offset=0, ...)`): у WRITE-FLASH offset
   является частью XML, а не выводится из ack'ов — надёжнее для точечной записи. Учитывать
   scrubber из re-writeflash-scrubber.md.
4. Для «space»-семантики: можно слать `<source_file>MEM://0x0:0x800</source_file>` с
   `<space_list><space offset="0x0" length="0x800"/></space_list>` внутри arg — парсер proven
   (§2); это явный способ ограничить область записи первыми 0x800 байтами.

## 6. Безопасный откат misc из /home/musin/misc_before.bin

Файл: 524288 байт = полный размер misc (0x80000), снят до инцидента (proven: BCAB @0x800
и нули в 0x0-0x7FF соответствуют состоянию «до»).

1. Загрузиться в DA2 (boot ROM mode, как обычно для RMX3630).
2. Прочитать текущий misc (READ-PARTITION/READ-FLASH, 0x80000) и сохранить как
   `misc_damaged.bin` — для forensics (diff 0x80C/0x818).
3. Восстановление: `WRITE-FLASH` `partition="misc"`, `offset=0x0`, полные 0x80000 из
   `misc_before.bin` (вариант §5.3 — самый контролируемый: erase+program в одном хендлере,
   явный offset). Перед записью убедиться, что размер совпадает; после — прочитать обратно и
   сравнить sha256 с `misc_before.bin`.
4. Если WRITE-FLASH упрётся в deny/scrubber — патчи из re-writeflash-scrubber.md §5
   (`0x4000325c` для WRITE-FLASH / `0x40002308 blx r2` region для WRITE-PARTITION).
5. Проверка после отката: BCAB @0x800 байты `5f61 0000 4243 4142 0102 0000 9f00 0e00 ...`
   должны совпасть с бэкапом (т.е. вернуть `9f00 0e00` на 0x80C и прежние 4 байта на 0x818).

## 7. Неопределённости

- Точная семантика числа в `OK@...`-ответе на обмен `0x4003053c` (offset или length) —
  inferred; нужен лог DA (`cur_offset_low`).
- Судьба 8 байт на 0x80C/0x818 — inferred (erase-сайд-эффект/OPLUS-bookkeeping); код,
  который их пишет, не локализован.
- Внутренности program-диспетчера `0x4002aac0` и erase `0x4002eca4` до уровня UFI-команды
  не трассированы (как и в re-write-chain.md §8).
- Точная точка, где engine-2 вызывает program (между USB-recv и advance), по дизассемблу
  0x4003010c видна только через `[0x40054320]`/слот — вызов program-диспетчера отнесён к
  lit-pool 0x40054328 (per re-write-chain.md), подтверждения инлайном нет.
