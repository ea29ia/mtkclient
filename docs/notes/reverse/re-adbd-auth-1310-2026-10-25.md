## 1. Short answer

`adbd` decides "is authorization required?" **once, in `adbd_main`**, from a
single global byte `auth_required`. It is `1` at load and is only ever assigned
from `GetBoolProperty("ro.adb.secure", false)` — and only when the device is
unlocked (`ro.boot.verifiedbootstate == "orange"`) **or** `ro.debuggable=1`.
With `ro.adb.secure=1` (this build) the gate is on.

When the gate is on, the host key is checked against **two hard-coded paths** in
`/system/lib64/libadbd_auth.so`: `/adb_keys` **first**, then
`/data/misc/adb/adb_keys`, with no property and no `ro.debuggable` check.
Therefore a host key placed in `/adb_keys` on the ramdisk is accepted with **no
screen interaction, no property change and no `/system` change** (static
conclusion; never exercised on this unit — (unverified)).

A second, independent boot-side switch exists: `/force_debuggable` +
`/adb_debug.prop` (root of the initramfs) make init load `ro.adb.secure=0` as
the *last* property file, which turns `auth_required` off entirely.

## 2. Q1 — the auth decision

### 2.1 Storage

| what | address | initial bytes | evidence |
|---|---|---|---|
| `bool auth_required` | `0x1e5404` (1 byte) | `01` | `.data`; symbol size 1 |
| `bool socket_access_allowed` | `0x1e5405` | `01` | adjacent globals, matches `daemon/auth.cpp:56-57` |

`adbd_main` reaches the global through GOT slot `0x1e2c80` (store at
`0xa0338`); the packet path reads the variable directly at `0x1e5404`.

### 2.2 `adbd_main` (`0xa01b4`)

```
a0218  build string "ro.boot.verifiedbootstate"   (rodata 0xcf82, len 25)
a0258  bl  android::base::GetProperty(name, default="")
a0270  cmp len,#6
a0290  bl  std::string::compare(0,-1,"orange",6)  (rodata 0x13541)
a029c  cset w19, eq                     ; w19 = (vbstate == "orange")
...
a02f0  bl  __android_log_is_debuggable  ; reads ro.debuggable
a02f4  cbz w0, 0xa0348                  ; not debuggable -> skip
a02f8  "ro.adb.secure"                  (rodata 0x13f89, len 14)
a0324  bl  android::base::GetBoolProperty(name, false)   ; w1 = wzr
a0334  ldr x10, [GOT 0x1e2c80]          ; &auth_required
a0338  strb w9, [x10]                   ; auth_required = value
```

Reconstructed (identical to `packages/modules/adb/daemon/main.cpp:216-226`,
android14-release):

```c
bool device_unlocked =
    android::base::GetProperty("ro.boot.verifiedbootstate", "") == "orange"; // 0xa0218..0xa029c
if (device_unlocked || __android_log_is_debuggable()) {                      // 0xa02f0..0xa02f4
    auth_required = android::base::GetBoolProperty("ro.adb.secure", false);  // 0xa02f8..0xa0338
}
/* else: auth_required keeps its static initializer: true */
```

### 2.3 Exact truth table (the "unset" question)

`GetBoolProperty(name, false)` means the default inside the branch is **false**;
but that branch is only entered when unlocked or debuggable. Outside it, the
compiled-in `true` stands.

| `ro.adb.secure` | `verifiedbootstate=="orange"` or `ro.debuggable=1` | `auth_required` | result |
|---|---|---|---|
| unset | yes | **false** | no auth |
| `0` | yes | **false** | no auth |
| `1` | yes | true | auth |
| unset | no (locked, user build) | **true** (default) | auth |
| `0` | no | **true** (branch not taken) | auth |

So on a locked `ro.debuggable=0` build, `ro.adb.secure=0` is a no-op; on this
device (bootloader unlocked → `orange`, or `ro.debuggable=1` supplied via
`adb_debug.prop`) it is the master switch.

### 2.4 How the byte is consumed (`handle_packet`, `0xa4ec4`)

```
a5844  adrp x8,0x1e5000 ; add #0x404       ; &auth_required
a584c  ldrb w8,[x8]
a5850  cbz  w8, 0xa58b4                    ; auth disabled -> go online
a5858  bl   send_auth_request(t)           ; 0xbc260: sends A_AUTH TOKEN
...
a58b4  (verbose log)
a58c8  bl   handle_online(t)               ; 0xa37e8
a58d0  bl   send_connect(t)                ; 0xa430c
```

A_AUTH sub-command dispatch (same function):

* `arg0 == 2` (ADB_AUTH_SIGNATURE, `0xa4ff0`): builds the signature string and
  calls `adbd_auth_verify(token20, sig, &auth_key)` at `0xa502c`; **success
  goes straight to `adbd_auth_verified(t)` at `0xa5038`** → `handle_online` +
  `send_connect`. No framework, no UI, no screen.
* `arg0 == 3` (ADB_AUTH_RSAPUBLICKEY, `0xa4fe8` → `0xa5324`): stores the key and
  calls `adbd_auth_confirm_key(t)` at `0xa5350` → `adbd_auth_prompt_user_with_id`
  → system_server dialog. **This is the branch that a dead screen makes
  impossible.**

`adbd_auth_verify` is local at `0xbbe8c`; it calls
`adbd_auth_get_public_keys@plt` at `0xbbf20` (see §3).

### 2.5 Other gates — what does and does not affect auth

| gate | evidence | effect on auth |
|---|---|---|
| `ro.debuggable` (`__android_log_is_debuggable`) | `0xa02f0`, `0xa03fc`, `0xa0528` | Part of the OR that enables the `ro.adb.secure` read. Does **not** override `ro.adb.secure=1`. Also used by the framework and for capability dropping. |
| `service.adb.root` | `0xa0404` / `0xa0418` (`GetProperty("service.adb.root","")`, rodata `0x11fb0`) | Privilege only: `adb_root` keeps uid 0 iff `ro.debuggable=1`; `adb_unroot` forces drop. No auth effect. |
| `ro.secure` | `0xa03b8` (`GetBoolProperty("ro.secure", true)`, rodata `0x1056e`) | Privilege only. With `ro.secure=1` adbd drops to uid/gid **2000** (AID_SHELL) at `0xa0540`/`0xa0550` (`minijail_change_gid/uid`, `minijail_enter` `0xa0558`). This is why the key file must be readable by uid 2000. |
| `persist.adb.secure` | **absent** from `adbd_sys` and `libadbd_auth.so` (string scan) | no effect (the property does not exist in this build) |
| `adb_allowed_connection_time` | **absent** from both binaries, from the whole `/tmp/opencode/sysa` tree (`rg -a`), and from the android14 adb tree | not a device-side knob at all |
| `service.adb.tcp.port`, `persist.adb.tcp.port`, `service.adb.listen_addrs` | `0xa086c`, `0xa08ec`, `0xa078c` | add TCP/vsock listeners; authorization is unchanged |
| `sys.usb.adb.disabled`, `sys.usb.ffs.ready` | `0xc5464`, `0xcb4c0` | USB transport availability only (functionfs thread); no auth effect. Gadget composition itself is `sys.usb.config`, owned by init/vendor scripts. |
| `persist.adb.tls_server.enable` | `adbd_sys` string + wireless-debugging code | TLS listener for `adb pair`; USB auth unchanged |
| SELinux (`u:r:adbd:s0`) | APEX `etc/init.rc` `seclabel u:r:adbd:s0` | does not gate auth; gates reads of `/adb_keys` (see §4) |

`ro.adb.secure` is context `u:object_r:build_prop:s0` in
`plat_property_contexts:976`. That context governs *property-socket* writers; init
writes it in-process (`PropertySetNoSocket`), which performs **no** SELinux check
(see §7.2).

## 3. Q2 — where the authorized-keys path comes from

### 3.1 It is not in `adbd`

`adbd_sys` contains **no** `/data/misc`, no `adb_keys`, no `adb.dir`
(`grep -aob` → nothing). Reason: the authorization logic lives in a shared
library:

```
readelf -d adbd_sys | grep NEEDED
  libc.so libdl.so libm.so libcrypto.so libadbd_auth.so libadbd_fs.so
  liblog.so libselinux.so libc++.so
```

The APEX **requires but does not ship** those libraries. Decoding
`apex_manifest.pb` (minimal protobuf walk; version `341520010`, min/target SDK
`30`/`34`):

* field 7 (`provideNativeLibs`) = `libadb_pairing_auth.so`,
  `libadb_pairing_connection.so`, `libadb_pairing_server.so`,
  `libadbconnection_client.so`;
* field 8 (`requireNativeLibs`) = `libadbd_auth.so`, `libadbd_fs.so`, `libc.so`,
  `libdl.so`, `liblog.so`, `libm.so`, `libselinux.so`.

`debugfs ls /lib64` of the payload confirms the required libs are absent
(payload only has pairing libs, `libbase`, `libc++`, `libcrypto`,
`libcrypto_utils`, `libcutils`). So `libadbd_auth.so` is resolved from
**`/system/lib64/libadbd_auth.so`** (the file analysed here, 275,848 B).
The vendor-ramdisk mini-`/system` also has an older copy (250,696 B); it is
shadowed by the real `/system` mount and is not the one that runs.

### 3.2 The path is a compile-time array, not a property

`adbd_auth_get_public_keys` is exported at **`0x100e0`** (a 4-byte
`b 0x100f0` after the BTI/padding; implementation at `0x100f0`). The important
part:

```
100f0  prologue; x27 = *(GOT 0x3fcb8)          ; GOT slot holds 0x3e078
1013c  x25 = x27
10144  x25 += 8
10148  x8 = x27 + 0x10                          ; exactly two 8-byte entries
1014c  cmp x25,x8 ; b.eq 0x10418                 ; return when both done
10154  x21 = *x25                               ; path
10158  w1 = 4 (R_OK)
10160  bl access                                ; access(path, R_OK)
10164  cbnz w0, 0x10144                         ; not readable -> next path
10170  bl ShouldLog ; 0x101f4 ReadFileToString(path,&content)
10250  loop: ldrb/len of line; 1026c blr x20    ; callback(opaque,line,len)
       Split delimiter is "\n" (std::string SSO len=1, byte 0x0a)
```

`.data.rel.ro` at **`0x3e078`** (resolved by GOT slot `0x3fcb8`, which holds
`0x3e078`):

```
0x3e078: 49 33 00 00 00 00 00 00   -> 0x3349 "/adb_keys"
0x3e080: 03 36 00 00 00 00 00 00   -> 0x3603 "/data/misc/adb/adb_keys"
```

Log strings in the same library confirm the code identity:
`0x2779 "adbd_auth: loading keys from "`, `0x27a5 "adbd_auth: couldn't read "`,
source path `0x303d "frameworks/native/libs/adbd_auth/adbd_auth.cpp"` (lines 397/400).

Cross-check: `frameworks/native/libs/adbd_auth/adbd_auth.cpp:393`
(android14-release)

```cpp
static constexpr const char* key_paths[] = {"/adb_keys", "/data/misc/adb/adb_keys"};
void IteratePublicKeys(bool (*callback)(void*, const char*, size_t), void* opaque) {
    for (const auto& path : key_paths) {
        if (access(path, R_OK) == 0) { ... ReadFileToString ... Split(content,"\n") ... }

```

**No property, no `getenv`, no argv, no linker-provided variable.** The only
`getenv` in this library is for `ANDROID_SOCKET_adbd`. The path cannot be
redirected by a `persist.*`/`service.*` property — but it does not need to be:
`/adb_keys` is already path[0].

## 4. Q3 — is `/adb_keys` consulted by this build?

**Yes — unconditionally, and first.**

* In `libadbd_auth.so` the array is iterated in order (`0x1013c`..`0x10164`);
  there is no conditional between `access()` and the read other than
  readability. There is no `ro.debuggable`/`ro.adb.secure` test in this
  function (the only branch is the logging guard at `0x10170` and the error
  path at `0x1039c`).
* It is reached only when a signature must be checked, i.e. when
  `auth_required == true` and the host sends `ADB_AUTH_SIGNATURE`:
  `handle_packet 0xa502c` → `adbd_auth_verify 0xbbe8c` →
  `adbd_auth_get_public_keys@plt 0xbbf20` → `IteratePublicKeys`.
* Success is a local RSA check (`RSA_verify(NID_sha1, token20, sig, key)`),
  then `adbd_auth_verified(t)` at `0xa5038` → online.
* **The "only on `ro.debuggable=1`" story is false for this era.** The same
  two-path array with no gate already exists in
  `android10-release system/core/adb/daemon/auth.cpp:56`. What is true is that
  `/adb_keys` is normally only *shipped* in the ramdisk of debuggable/eng
  images — presence, not a runtime check, is what differs.

Runtime requirements for the `/adb_keys` route (all satisfied by a plain file in
the initramfs):

1. file present at `/adb_keys` in the **runtime root** (the initramfs; not
   under the mounted `/system`);
2. readable by uid 2000 after `drop_privileges` — mode `0644` (the existing
   built ramdisk file is `-rw-r--r-- root root`);
3. labeled `adb_keys_file`: `init.rc` does `restorecon /adb_keys` in
   `on early-init` (`/tmp/opencode/sysa/system/etc/init/hw/init.rc:49`) using
   `plat_file_contexts:390  /adb_keys  u:object_r:adb_keys_file:s0`;
4. SELinux allow rule for the daemon:
   `plat_sepolicy.cil:17073 (allow adbd adb_keys_file (dir (… search)))` and
   `:17074 (allow adbd adb_keys_file (file (ioctl read getattr lock map open watch watch_reads)))`.
   (Note: no `allow adbd rootfs:file read` exists — if `restorecon` is skipped the
   read will be denied. `/data/misc/adb` is also `adb_keys_file`, line 174.)

The stock vendor_boot_a ramdisk (`/tmp/opencode/vb/frag0.cpio`) has **no**
`/adb_keys`; the previously built `v7.cpio` has one at its root (714 B, our
`musin@tomato` key, 0644). Same file, if visible at `/adb_keys`, authorizes
immediately.

## 5. Q4 — can a modified `adbd` ever be activated?

### 5.1 What protects the APEX

* `/system/etc/security/apex/` **does not exist** in this build. Contents of
  `/system/etc/security` are only `cacerts/`, `cacerts_google/`, `fsverity/`,
  `otacerts.zip`; there is no `*.avbpubkey` anywhere in the tree
  (`find` → nothing). So there is no on-device key store to satisfy — the pin
  is the key *inside* the pre-installed APEX.
* Payload (`apex_payload.img`, 8,544,256 B, ext4) verification (re-parsed from
  the image; matches the earlier `avbtool info_image` run):

```
AVB0 footer @ 8,536,064 (size 2,240)
  auth block 576, aux block 1,408, algorithm 2 = SHA256_RSA4096
  hashtree descriptor (tag 1, len 232):
    image 8,462,336  tree_off 8,462,336  tree_size 73,728  blocks 4096/4096
    hash sha256  flags 0
    salt 66f97e8d…b072e72d18d639ed94f5610c9ee3b5189dd8
    root a2091f56…afea29373475c6
  public-key struct at payload 8,537,216 (1032 B) == zip's apex_pubkey
    sha1 d0b0b877bc6a48b1ecd17632205e5fb4d92b9273 (RSA-4096)
```

  So the payload is **AVB-hashtree signed by the key bundled in the same ZIP**
  (self-referential, as the earlier note said), and it is **not fs-verity**
  (`"fs-verity"` / `".fs-verity"` do not occur in the payload).
* `apexd` on device contains the pin strings
  `public key doesn't match the pre-installed one`,
  `: public key doesn't match pre-installed one`,
  `public key doesn't match:`, `is not pre-installed` — i.e. an update APEX in
  `/data/apex/active` is only accepted if its bundled pubkey equals the
  pre-installed one (**Google's**, sha1 `d0b0b877…`) *and* its payload verifies
  against that key.
* `ro.apex.updatable=true` (`build.prop:130`) means `/data/apex/active` is
  scanned; that does not help without Google's private key.
* "apexd skips verification for preinstalled APEX on unlocked devices" is
  **false**: `MountPackage()` always calls `VerifyApexVerity()` with the
  bundled key (the android14 source comment is explicit: *"we don't skip
  verification to ensure that APEXes are correctly signed"*). AVB permissiveness
  on an unlocked device applies to *partition* vbmeta, not to the embedded APEX
  payload verification.

### 5.2 Verdict

| route | verdict |
|---|---|
| edit `bin/adbd` inside the APEX in place | **NO** — payload hashtree + RSA-4096 signature fail |
| replace `/system/apex/com.google.android.adbd.apex` with a re-signed APEX | **NO without flashing** — apexd would accept a self-consistent ZIP (key travels inside), but `/system` is dm-verity protected (`vbmeta_system` hashtree, `Flags: 0`); a modified block is unreadable. Requires flashing `system_a` + a re-generated/re-signed `vbmeta_system`. |
| push an update APEX to `/data/apex/active` | **NO** — pinned to Google's `apex_pubkey`; we have neither the key nor the signing key |
| make the vendor-ramdisk `adbd` (2,108,208 B) run | **NO** — `/system` is mounted over the mini-`/system` before adbd starts; it is a different (older) adbd anyway |
| replace the *key file* / *property* (this note) | **YES** — no APEX/system change at all |

Consequence: patching `adbd` is a dead end; the auth gate must be changed from
outside the APEX. That is exactly what `/adb_keys` and `adb_debug.prop` do.

## 7. Boot-side recipes (what actually flips the gate)

### 7.1 Option A (recommended, property-independent): `/adb_keys`

1. Put the host public key (`~/.android/adbkey.pub` content, one line, optional
   ` user@host`) at **`/adb_keys` in the root of the initramfs** — the ramdisk
   that the bootloader hands to the kernel and that init keeps as its root.
2. `chmod 0644`, owner `0:0`.
3. Nothing else: `init.rc` early-init `restorecon`s it (line 49), the plat
   policy already allows `adbd → adb_keys_file` read, and `libadbd_auth.so`
   tries it before `/data/misc/adb/adb_keys`.
4. Works with `ro.adb.secure=1` untouched. If the key is not ours the host
   falls back to the prompt; with ours the signature path succeeds and
   `handle_packet` goes online at `0xa5038` with no UI.

Caveat: the file must be in the ramdisk that is **effective** at runtime. The
stock vendor_boot_a ramdisk is `/home/musin/slot_vendor_boot_a.img`
(`/tmp/opencode/vb/frag0.cpio`); its `/init` is a symlink to
`/system/bin/init` and it carries a mini-`/system` (adbd 2,108,208 B, init
2,097,128 B). The earlier `v7.cpio` (3.1 MB, init 3,143,536 B) contains
`/adb_keys`, `/force_debuggable` and `/adb_debug.prop`. Which archive is
unpacked last (and therefore which `/init`/`/system/bin/init` runs first stage)
must be confirmed by booting; put a copy of `/adb_keys` in every candidate
ramdisk root to make the test independent of that question.

### 7.2 Option B: `/force_debuggable` + `/adb_debug.prop`

The AOSP "debug ramdisk" mechanism, verified in **this** init binary:

First stage (`/system/bin/init`, 3,085,160 B):
```
124554  bl access("/force_debuggable", F_OK)          ; string @0x17a49
124568  cbnz w0, skip
12456c  "/adb_debug.prop"                             ; @0x2f57b
1245d8  adr x1, 0x337b7  "/debug_ramdisk/adb_debug.prop"
124600  bl std::filesystem::copy_file (0x1b2020)
```
The same block exists in the vendor-ramdisk init (2,097,128 B) at
`0xf1624` (`/force_debuggable`) / `0xf164c` (`/adb_debug.prop`) /
`0xf168c` (copy), so whichever init runs first stage supports it.

Second stage, `PropertyLoadBootDefaults`:
```
156d5c  load_properties_from_file("/system/build.prop", …, &map)
   …
156fe4  bl access("/debug_ramdisk/adb_debug.prop", R_OK)   ; @0x338ee
157028  load_properties_from_file(…, &map)                  ; LAST file wins in map
```
Then the whole map is applied once via `PropertySetNoSocket`
(`property_service.cpp:1201-1206`). `ro.*` is "write-once"
(`property_service.cpp:396-403`), but each name is set only once here, so the
map value wins; `PropertySetNoSocket` performs no SELinux/property_context check.

So `/adb_debug.prop` at the **ramdisk root** (copied to the `/debug_ramdisk`
tmpfs, which is mounted at first stage `first_stage_init.cpp:290-292`) with:

```
ro.adb.secure=0
ro.debuggable=1
ro.force.debuggable=1
```

turns `auth_required` off before adbd starts. Two easy mistakes, both fatal:

* putting `adb_debug.prop` **inside** the ramdisk's `debug_ramdisk/` directory —
  that path is a tmpfs mount point, the file is shadowed; it must be
  `/adb_debug.prop` at the root plus an empty `/force_debuggable`;
* omitting `/force_debuggable` — without it the copy never happens.

`/debug_ramdisk/userdebug_plat_sepolicy.cil` is optional (only copied if present
in the ramdisk); it is not needed for the property override.

## 8. Corrections / caveats

1. **`re-adb-unauthorized-checklist.md` §6 is wrong** where it says
   `ro.adb.secure` was "dropped by the property service (SELinux `build_prop`)".
   In this init, boot properties are merged in a `std::map` with later files
   overriding earlier ones *regardless of `ro.`* (`property_service.cpp:1111-1117`)
   and applied in-process with no SELinux check. The real failure modes are
   (a) `adb_debug.prop` inside `debug_ramdisk/` (shadowed by tmpfs) and
   (b) missing `/force_debuggable`, and (c) patching a ramdisk that is not the
   effective first-stage root.
2. `re-adbd-apex-route.md` §3.1/§3.2 re-verified: no `/system/etc/security/apex`,
   no external pubkey store, APEX self-signed with a bundled key pinned by
   apexd. The APEX file in this note is the 2025-02-25 build
   (`ab4ce374…`) not the 2024-09 export (`ce80eb5a…`); `bin/adbd` is identical.
3. The `ro.adb.secure` branch depends on the live
   `ro.boot.verifiedbootstate == "orange"`. At writing time we could only infer
   the campaign state was unlocked; it was later confirmed on the unit
   (`ro.boot.verifiedbootstate=orange`, `seccfg lock_state=3`, LK
   `img_auth_required=0` / `avb_ret=0`). On a green device, option B must
   include `ro.debuggable=1` (it does) to enter the branch; option A does not
   care.
4. The `/adb_keys` file is read by uid **2000**, not root, because
   `ro.secure=1` forces the drop (`0xa0540/0xa0550`). A `0600` file will not
   work; a `0644` file will.
5. No claim here was validated on hardware at the time of writing; everything
   is static. Later the same day Option B was confirmed on the unit (vendor_boot
   v14, props route → authorised adb shell), and Option A became moot once the
   permissive cmdline images (v18/v19) and Magisk (v22) supplied root. The one
   runtime unknown that this note could not settle offline is which ramdisk
   archive supplies the effective `/init`, `/system/bin/init` and rootfs on this
   unit (see §7.1 caveat) — (unverified).
