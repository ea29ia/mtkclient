## 2. The container format (all-in-one-signature.bin)

`0x58881688`-magic containers, 0x60-byte header, little-endian:

| off | field | genuine values |
|---|---|---|
| +0x00 | magic1 `0x58881688` | checked at 0x4003CE70 / 0x4003E15C / 0x4003EB98 |
| +0x04 | payload size | cert1 = 0x6C5, cert2 = 0x434 |
| +0x08..+0x24 | 8.3 name ("aee", "cert1", "cert2", partition names for image sigs) |
| +0x28 | payload (X.509 DER) |
| +0x30 | magic2 `0x58891689` | checked at 0x4003CE84 / 0x4003E16C / 0x4003EBAC |
| +0x34 | dword | payload offset used by verify funcs (ce28: `0x4003CEBC add r1,r4,r0`) |
| +0x38 | dword | second offset/len (ce28 stores to `0x400712E8`) |
| +0x3C | **type/version dword** | cert1 = `0x02000000`, cert2 = `0x02000002` |
| +0x40/+0x44 | flags/offsets |

`all-in-one-signature.bin` = 69 containers: the outer `aee` blob (@0, size
0xF3740 = whole file), then per-partition pairs — `cert1` (type `0x02000000`)
followed by `cert2` (type `0x02000002`) for preloader/lk/logo/dpd/spmfw/scp/…
plus per-image signature containers (`0x1EAB1EAB` "bootimg" type handled by
`0x4003EB50`+0x28 branch, `0x4003EC34`).

**Crypto-key map (proven):**

| address | content | sha256(prefix) | role |
|---|---|---|---|
| 0x40052DB8 (2710) | 0x100 B | `97e49b50…` | **MTK root RSA-2048 modulus — byte-identical to the SPKI modulus inside the genuine cert1 X.509** (`aio+0x4C8`, verified equal) |
| 0x40052EB8 (2710) | 0x180 B | `d66995f0…` | alternate static key (3072-bit geometry) |
| 0x40053038 (2710) | 0x100 B | **`c58002ae…`** | the OPLUS **SET-FLASH-POLICY** modulus — byte-identical to 200EX01 `0x400529E0` (Alexander's finding reproduced). **Not consumed by the cert-chain cluster** (its only reader remains the policy verifier path) |

Installed at boot by `0x400075E4`: `memcpy(0x40067240, 0x40052DB8, 0x100)` and
`memcpy(sp, 0x40052EB8, 0x180)` then two `0x40035F7C(ptr, size)` registrations
(size whitelist: 0x100/0x180/0x200 → key slots 0x40067240/0x40066E9C/0x40067240-class,
`0x40035FE4` rejects others with `0xC0020026`). The cluster's key slots live in
.bss: modulus @0x40064970 (0x200), exponent @0x40064B70, signature @0x40064B74,
exp-len @0x40064D74 (filled by the DER parser `0x4003DA34`).

## 3. `0x4003CE28` — cert1 verify (full check ladder)

Base error `r5 = 0xC0020013` (built `0x4003CE5C movw r5,#0x13 / movt #0xC002`).
Ladder (each `add r7, r5, #n` site quoted):

1. `memset(0x40064970, 0, 0x404)`, then `[+0x200]=0x200`, `[+0x404]=0x200` defaults (`0x4003CE48-0x4003CE68`).
2. magic1 == 0x58881688 (`0x4003CE70`), else **+2** → `0xC0020015`.
3. magic2 == 0x58891689 (`0x4003CE84`), else **+2**.
4. `[+0x3C]` stored to `0x4005760C`; **geometry gate**: `(val|1) == 0x02000001` required (`0x4003CEA8-0x4003CEB8`), else **+0** (`0xC0020013`). So ce28 only processes type `0x02000000`/`0x02000001` containers.
5. payload ptr = container + `[+0x34]`, size = total − off (no clamp — see F2), stored to `0x400712E4/E8` (`0x4003CEBC-0x4003CEE4`).
6. `0x4003D710(container, &len, 1)` — key-geometry select: reads container magic
   fields, requires `[len] <= 4` (`0x4003D780 cmp r2,#4; bhi → +4 → 0xC0020057`),
   parses exponent bytes, writes the **hardcoded** per-key-geometry constants
   (`0x4003D818-0x4003D854`: key-id → sizes 0x100/0x180/0x200, hash lens
   0x20/0x30, key-slot ptr 0x40067240/0x40066E9C/0x40067240-class — **all
   constants, no host-controlled geometry**), and key-id gates via
   `[0x40057604]`/`[0x4007117C]` state.
7. `0x4003DA34()` — parses the X.509 DER from `0x400712E4`: copies to
   0x400712F0-class buffer, byte-reverses (`0x4003DB30` swap loop), verifies
   via `0x4003B420(DER, sha, [0x4007117C], desc)` → **the certificate signature
   is RSA-verified** (dispatch `0x4003B470`: key-id 0 → `0x4003AF54`
   (pkcs_1_pss_decode_sha256), 1/2 → `0x400401C8` (sha384)). Modulus+exponent+
   signature extracted to the 0x40064970-class slots.
8. hash-list / extension stage (`0x4003DB5C` inside the caller path; tag walker
   `0x4003CC4C` + reader `0x4003CD9C`): scans DER for the tag structure, reads
   **≤0x200 bytes** (hard clamp: `0x4003CDD8 cmp ip, r2; bls` / error `+1`
   `0xC00200A2-class`), compares against session state (modulus compare loop
   `0x4003D120-0x4003D188` full-length `0x100/2`-step; extension bytes
   `0x4003D288` byte loop; **any mismatch → immediate reject**).
9. `0x4003EA10` — anti-replay: scrambles `[0x40071534]` (previous-stage sig
   buffer) through `0x40039FD0` (HW-mixed PRNG via `0x40031770`) and compares
   against `[0x400714F4]`; mismatch → `0xC002001B/1C`.
10. exponent/hash checks then **RSA verify of the container payload** via
    `0x4003C900` (`0x4003D65C`, only when `[0x4005760C]==0x02000000`):
    `cc4c(2)`→`cd9c(4)` reads, then the PKCS#1 block verifier
    (`0x4003B324`, shared with the 2710 image path `0x40039720`):
    * `block[0]==0x00 && block[1]==0x01` (`0x4003B36C-0x4003B37C`)
    * filler bytes must be 0xFF **or 0x00** (`0x4003B3A0 cmp r1,#0xff; cmpne r1,#0; bne fail` — the known RFC-8017 deviation, all filler still range-checked, so no Bleichenbacher middle-garbage forgery)
    * first 0x00 terminator must be at offset **0xCD** (`0x4003B3B8 cmp r0,#0xcd`)
    * `memcmp(sp_digestinfo, block+0xCD, 0x13)` — DigestInfo = 19-byte SHA-256
      prefix `3031300d060960864801650304020105000420` stored at **0x40054268**
      (copied `0x4003B334 ldm 0x40054268!`; byte-verified equal)
    * `memcmp(expected_hash, block+0xE0, 0x20)` — **full 32-byte compare**
      (`0x4003B3E8-0x4003B3F4`)

No MD5 anywhere in the cluster (no MD5 init constants; SHA-256/SHA-384 only).
No parse-error→accept fall-through: every stage's failure has an explicit
error return (`0x4003D220`/`0x4003D244` exit collects `r7`).

## 4. `0x4003E110` — cert2 verify + hash list

Base error `r5 = 0xC0020014`. Ladder:

1. memset(0x40064970, 0, 0x404) (`0x4003E130`); defaults `[+0x200]=[+0x404]=0x200`.
2. magic1/magic2 (`0x4003E15C-0x4003E17C`) else +1/+2.
3. `[+0x3C]` → `0x4005760C`; **requires exactly `0x02000002`** (`0x4003E1B8 cmp r1, #0x02000002`), else +0. So e110 processes only `cert2`-type containers.
4. payload ptr/size → `0x400712E4/E8` (unchecked `+0x34` — F2).
5. `0x4003DA34()` parses the DER → modulus/exponent/signature slots.
6. **Device-key binding** (the strong check): parsed `n_mod` (global+0x200) must
   equal `ctx+0x210` (`0x4003E1D4`), parsed `n_exp` (+0x404) == `ctx+0x414`
   (`0x4003E1E4`), and the parsed **modulus must byte-equal `ctx+0x10..0x210`**
   (loop `0x4003E204-0x4003E21C`), else +5/+6/+7. I.e. the uploaded cert2's SPKI
   key must be the key the session already registered — an attacker cannot
   substitute their own key here without already being the registered key.
7. extension-byte compare `ctx+0x214` vs parsed (+8, `0x4003E234-0x4003E260`).
8. `0x4003DABC` (payload sanity, `b504` size whitelist 0x100/0x180/0x200) then
   `0x4003DB5C` — hash-list locator/signature verifier (tag scan `cc4c(0x30)/cc4c(3)`
   + `cd9c` ≤0x200 + `b420/b444/b470` verify). Empirically (§6): if the
   hash-list structure is absent, db5c returns 0 and e110 continues — the
   hash list is **optional by design** ("hash list does not exist" string);
   absent list = nothing registered downstream (fail-closed for hash binding).
9. Post-verify tag stage (`cc4c(3)` + `cd9c(0x30)` → state+0x3C cert-version,
   `0x4003E4F8-0x4003E60C`), then e7f4 4-byte reads, `d710` geometry from
   version, final key-slot compare + `c900` (`0x4003D62C-0x4003D65C`).

## 5. `0x40037FC8` — image verify (GFH_MULTI_SEC)

Called from the preloader WRITE-FLASH engine (`0x4000BE14`, r0 = image state,
r1 = size). Walks GFH TLVs: `ldr r2,[r4]; and r2,r2,#0x4D4D4D4D; cmp #0x4D4D4D4D`
(`0x40037FF8`), `[+6]==0x60` found-branch, else advance `+[+4]` bounded by the
total size arg (`0x40038024 cmp r0, r5; bls`). On find: `0x40038FD4`/`0x400390A8`
parse the multi_sec blob, `0x4003B420` verify, and **`0x400391A8` compares the
image public-key hash against the FUSE public-key hash** (`sbc_en`,
`pl img pubk hash = / fuse pubk hash =` strings @0x40051F31-0x40051F9E; efuse
read at 0x11C10140-class). Emulator verdict: the fuse block reads 0 →
`pl pubk auth fail` — the gate can never pass offline; fuzzing showed uniform
`0xC0020012` rejects (25/27) with 2 cases reaching the crypto engine.

## 6. Emulation + fuzz (fuzz2.py; results in fuzz_results2.json / fuzz2.log)

**Ground truth and why full ACCEPT is not reachable offline (required
justification).** The build routes **all** crypto through the on-SoC engine at
MMIO `0x10210000`: the bignum core `0x4003F2E8` polls status register
`0x10210E9C` (`0x4003F398 ldr r2,[r5,#0xE9C]; tst r2,#0xF; beq 0x4003F398`).
Measured in Unicorn: **13,316,840 polls** of 0x10210E90/E9C within a 40M-instruction
window — an infinite busy-wait, because the engine never signals ready without
hardware. Every run that reaches the modexp/SHA therefore cannot complete.
Per the task's contingency, the harness was redesigned around this: results are
classified by **completion** (`pc == return-page`) and by a **stage ladder**;
"ACCEPT" is only credited when a run *completes* with r0==0. Reference stages
come from the genuine blobs themselves.

Stage ladder (from static analysis + runs): entry/magic/geometry (0xC0020013/14/15)
→ DER parse (…19) → modulus/extension binding (…1A/1B/1C) → tag/parse (…1E)
→ crypto engine (REACHED_ENGINE) → ACCEPT(0).

**GT controls:**

| control | result |
|---|---|
| genuine cert1 container (aio+0x200, 0x3540 window) through ce28 | **REACHED_ENGINE** — passes every pre-crypto check (parse, modulus/ext binding, geometry) and enters the engine |
| genuine cert2 container (aio+0xAD0, 0x434) through e110 with ctx seeded from its own SPKI modulus/exponent | REJECT `0xC002001E` at the post-verify tag stage; all binding checks (§4.6) passed en route — b420 invocation counter = **0** (hash-list structure absent in this container → optional-list branch; flip of the trailing 0x200 B changes nothing → the list, when absent, is not "verified" but also not loaded) |
| single-byte flips of genuine cert1 (41 offsets) | all REJECT or REACHED_ENGINE, **0 completed-ACCEPT** |

**Mutation fuzz totals (all completed-or-classified, exit 0):**

| target | cases | REJECT | REACHED_ENGINE | CRASH | completed-ACCEPT |
|---|---|---|---|---|---|
| ce28 | 74 | 43 | 29 | **2** | 0 |
| e110 | 59 | 55 | 2 | **2** | 0 |
| 7fc8 | 27 | 25 | 2 | 0 | 0 |

REACHED_ENGINE cases (ce28 ×29) = mutations that leave the container
structurally valid (inert header fields, DER-body flips) — their only possible
failure is the post-modexp compare, which is engine-blocked offline; statically
that compare is full-length (§3.10), so no bypass is postulated. e110's
REACHED_ENGINE (off0x34=0x0/0x3ff) = degenerate offsets that steer the parse
into the engine path; no accept.

**Findings:**

* **F1 (design note, not a bypass):** hash-list verification is optional in
  e110 — a cert2 container without the list structure proceeds (b420 never
  invoked; proven by invocation counter = 0 on genuine and flipped inputs).
  Consequence is fail-closed (no hash list registered ⇒ no hash binding), not
  fail-open.
* **F2 (robustness/DoS):** container `+0x34` (payload offset) is used
  unvalidated: ce28 `0x4003CEBC add r1,r4,r0` / e110 `0x4003E19C add r2,r4,r0`,
  no `cmp` against the blob size; offsets `0xFFFFFFFF`/`0xFFFFFFF0` produce a
  wild pointer that is dereferenced in the tag walker at **0x4003CC88**
  (`cc4c`'s `ldrb r3,[r1]`) → fault. Both functions, reproducible
  (`off0x34=…` cases). Read-only; no OOB **write** found anywhere in the
  cluster (all writes are fixed-address .bss slots with fixed/clamped sizes:
  dabc 0x200 fixed, db5c cd9c clamp ≤0x200, e7f4 ≤4 B, eb50 fixed 0x34/0x10).
  Attack path: container data originates in the host-uploaded AllInOne blob
  (SET-ALLINONE-SIGNATURE, host-controlled) → crafted container → crash of the
  DA during image verification. DoS only.

## 7. Anti-loop record

1. xref search returned empty twice (missing cond-field mask in the BL scanner,
   then missing `&7`) → rewrote scanner with `top&7==5`; callers found.
2. First GT attempt "ACCEPTed" 27 mutants — traced to instruction-cap truncation
   (all "ACCEPTs" ended at PC 0x4003F3A0 mid-bignum, r0 coincidentally 0) →
   harness redesigned to completion-aware classification; GT re-anchored to the
   stage ladder. The same-failure-twice rule was applied to the engine problem:
   after the first infinite-poll discovery I did not retry longer timeouts;
   I switched to hook-based observation and classification instead.

## 8. Verdicts and invariants

| function | verifies | key source | bypass shape found? | verdict |
|---|---|---|---|---|
| 0x4003CE28 | container magics, geometry `(v|1)==0x02000001`, DER parse, modulus/extension session binding, PKCS#1 v1.5 (SHA-256 prefix 0x40054268, term@0xCD, full 32-B hash cmp) | static MTK root @0x40052DB8 (== genuine cert1 SPKI); registered slots only (b504 whitelist) | no | **holds** |
| 0x4003E110 | magics, version==0x02000002, DER parse, **parsed modulus must equal session-registered modulus**, extension bytes, optional hash-list sig | parsed cert2 SPKI must equal ctx-registered key (attacker cannot substitute) | no | **holds** |
| 0x40037FC8 | GFH TLV walk, multi_sec parse, image sig, **fuse pubk-hash equality** | efuse fuse hash (0x11C10140-class) | n/a offline | **gated** |
| 0x4003EB50 (aux) | container→state copy | — | fixed-size copies only | holds |

**Which invariant saves it:** (a) the modulus-binding compares in both verifiers
are full-length byte loops against session-registered/static key material —
there is no truncation, no "compare first N bytes", and no accept-on-parse-error
path (every ladder rung has an explicit reject); (b) key geometry and key slots
come from hardcoded per-key-id constants (`0x4003D818-0x4003D854`) gated by the
`b504` size whitelist — the host cannot downgrade to a weaker geometry; (c) the
PKCS#1 block check enforces the full filler range and the exact terminator
offset, closing the classic Bleichenbacher e=3/garbage-filler shapes; (d) the
OPLUS policy key (c58002ae…) is simply not an input to this cluster.

The one exploitable-looking residue is F2 (wild read from `+0x34`) — DoS-class,
not an auth bypass.
