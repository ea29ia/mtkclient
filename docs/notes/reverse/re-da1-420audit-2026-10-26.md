## 3. Diff vs 200EX01 and C.25

**vs 200EX01 (`docs/notes/rmx3630-da2/DA_BR.bin`):** every resolved address is
**identical, delta 0x0** — registrar, reg_cmd, table head, cmd_loop, blx_cb, dpc,
dpc_node, malloc/free/fire/insert/heap_init, heap_head/arena, download, recv store,
packet_len, DRAM-REPAIR handler, BOOT-TO, SHA-256, digest slot. Same 12-command
table, same string VAs. The only byte differences in the whole 428,284-byte DA1
body are **132 bytes in 38 regions**:

- the 32-byte **DA2 digest slot** at VA 0x2688CC (new value `27103e18…` — 420EX01's
  DA2 body differs from 200EX01's; the slot correctly binds its own DA2);
- build-marker strings: workspace `Build_S_Vendor/15810` → `Build_S_Vendor/27386`,
  build time `Sep  2 2024 22:21:03` → `Feb 25 2025 20:46:11` (1+5-byte pairs per
  occurrence).

So 420EX01's DA1 is the **same code as 200EX01's, re-built with new date strings
and a new DA2** — no fix, no new code, five months later. The 420EX01 preloader is
likewise 642 bytes / 45 regions off 200EX01's (all date/workspace markers).

**vs C.25 (`said/mt6789_realme.bin`, 2023-03-14):** pure address shifts of the same
code — allocator block −0x10C (`malloc 0x2041E8→0x2040DC`, `free/fire/insert/
heap_init` likewise), dispatch block −0xC4 (`cmd_loop 0x203C08→0x203B44`,
`DRAM-REPAIR handler →0x202BB8`, `BOOT-TO →0x200FEC`), blx −0xB8, download block
−0x26EC (`0x2500D8→0x24D9EC`, `recv_len_store →0x24DD08`), SHA −0x28C4
(`0x2522C4→0x24FA00`), digest slot −0x3CA4 (`0x2688CC→0x264C28`); data-segment
anchors identical (`dpc 0x2DF7A0`, forged node `0x2DF79C`, heap head `0x2DF7D0`,
arena `0x2E8000+0x10000`, `packet_length 0x2DE3F8`). Same classification as C.25:
VULNERABLE / UNCLAMPED / exploitable.

## 4. DAA key era — arithmetic, not assumption

PSS verification (RSASSA-PSS, SHA-256, salt 32 B, MGF1-SHA256, DB[0xBE]==0x01,
the `verify_daa_pss.py` model) of the 420EX01 `DA_BR.bin` trailers:

| trailer | × S (=K1, 200EX01-era, sha256 `97e49b50…`) | × K27 (=K2, 2710-era, `af102e73…`/sha `8b953efd…`) |
|---|---|---|
| DA1 @0x689B8 | **VERIFIED** | no-BC (structurally fails) |
| DA2 @0xBF980 | **VERIFIED** | no-BC |

**420EX01 is S-era.** The community model places the S→K27 roll between 2025-05 and
2025-10; 420EX01 is dated 2025-03-04 (built 2025-02-25) — the arithmetic confirms it
sits **before** the roll, and K27 does not merely "fail to verify" but fails
structurally (no 0xBC), i.e. it is a different modulus, not a near-miss.

Preloader moduli: the shipped `preloader_k6789v1_64.bin` (390868 B — same length as
200EX01's, 642 bytes of date/workspace diffs) contains S at the **same three
positions** as 200EX01 (0x5D1DC, 0x5D2DC live slot, 0x5F188) and **no K27 anywhere**.
The UFS/EMMC wrapper variants carry S too (`preloader.img`/`preloader_ufs.img` @
0x5E1DC/0x5E2DC/0x60188; `preloader_emmc.img` @ 0x5D9DC/0x5DADC/0x5F988 — K27 absent
in all). So the phone's own preloader trusts exactly the key that signed its own DA.

## 5. Verdict and timeline implication

| build | built | verdict | clamp | DRAM-REPAIR | key | digest slot |
|---|---|---|---|---|---|---|
| 200EX01 (our zip) | 2024-09-02 | VULNERABLE | UNCLAMPED | registered | **S/K1** | 0x2688CC |
| **420EX01 (our phone)** | **2025-02-25** | **VULNERABLE** | **UNCLAMPED** | **registered** | **S/K1** | **0x2688CC** |
| 2710EX01 (Alexander) | 2025-12-09 | PATCHED | CLAMPED | removed | K27/K2 | 0x2692F4 |

Two refinements to the community timeline:

1. **The recv clamp is per-vendor, not a global MTK code drop.** The 2025-01-03
   clamp datapoint (oukitel) does NOT generalize: oplus's MT6789 DA1 of
   2025-02-25 is still UNCLAMPED with the same code as 2024-09-02. The clamp that
   appears in oukitel/infinix3/doogee builds is a vendor-line change.
2. **Within the oplus MT6789 line, both fix stages land between 2025-02-25 and
   2025-12-09**: clamp+tripwire+command-removal+K27 rotation all arrive together in
   the 2710 generation. As of the firmware our phone runs, none of it exists.

## 6. Consequences for our own phone (RMX3630 @ 14.0.0.420EX01)

The phone is a **live testbed for the full chain with a known-good key**:

- Its shipped preloader carries S and verifies an S-signed DA1 — and the vendor's
  own 420EX01 DA1 IS S-signed, so the stock DA1 from `DA_BR.bin` passes DAA on the
  phone without any key work.
- That DA1 is statically VULNERABLE + UNCLAMPED with DRAM-REPAIR registered: the
  HeapBait chain is present in the exact binary the phone loads.

On-device attempt would look like (constants table — NOT run here; all values
resolved statically above and identical to the emulated 200EX01 chain):

| chain constant | 420EX01 value | = 200EX01? |
|---|---|---|
| DA1 load base | 0x200000 | yes |
| registrar / reg_cmd / table head | 0x200ED0 / 0x203BBC / 0x266070 | yes |
| cmd_loop / blx_cb / continuation | 0x203C08 / 0x2040D4 / 0x2040D8 | yes |
| dpc struct (cb / arg) | 0x2DF7A0 (0x2DF7A4 / 0x2DF7A8) | yes |

| heap head / sentinel / arena | 0x2DF7D0 / 0x2DF7D8 / 0x2E8000+0x10000 | yes |
| malloc / free / fire_write / insert / heap_init | 0x2041E8 / 0x204380 / 0x2043CC / 0x2043D8 / 0x2044C8 | yes |
| DRAM-REPAIR handler / BOOT-TO handler | 0x202C7C / 0x201080 | yes |

Flow: send the stock signed 420EX01 DA1 (passes the phone's S-era DAA), drive the
BOOT-TO/download path so the unclamped recv (`0x2503F4`) overflows the DRAM-REPAIR
buffer allocation, forge the free-list node at `0x2DF79C` to get the write-what-where
through `fire_write` (`0x2043CC`) or hijack the dispatcher's `blx` (`0x2040D4`),
with the only new constant being the DA2 digest value in the slot at 0x2688CC.
Residual unknowns are the same as for any silicon run: on-device heap state vs the
emulator layout (`re-da1-desync-2026-10-25.md` §measurements) — everything else is
now constant for the phone's own firmware.
