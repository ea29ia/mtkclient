**Date:** 2026-10-26
**Target:** `/tmp/opencode/mt6789_realme.bin` (DekuzenOkahiro's C.25 DA container)
**Harness:** offline Unicorn 2.1.4 (`/tmp/opencode/da1venv/bin/python`), no device, no network

## 0. Verdict

**C.25 is exploitable with the same chain as 200EX01 — unchanged L, unchanged
fake header, unchanged stub shape.**  The whole chain was re-proved by execution
on the C.25 DA1 inside Unicorn:

| stage | evidence |
|---|---|
| failing `CMD:BOOT-TO` stages 160 B (76 B stub + digest at +0x80) at `0x40000000` | `staged_equal=True`, `rc=0xC0070004`, `cmp_bytes=1` (first digest byte differs), slot untouched |
| `CMD:DEBUG:DRAM-REPAIR` with `L=0x3C` fires `dpc->cb = 0x40000000` | exactly 1 fire write on node `0x2DF79C`, victim = the live 0x30-byte XML node right above `D` |
| `cmd_loop` `blx r4` at `0x20401C` → stub at `0x40000000` | target `0x40000000`, stub entry/`bx lr` both hit, return to `0x204020` |
| stub writes the slot and clears dpc | `mem[0x264C28:…] == sha256(patched DA2 body)`, dpc `[0,0,0]` |
| DA survives | free list walks to sentinel `0x2DF7D8`, `malloc(0x100)+free` ×3, one more command answered `OK` |
| the *real* `BOOT-TO` then accepts the patched DA2 | `rc=0`, `dpc->cb=0x40000000`, `dpc->arg=0x2DE180`, 32/32 bytes compared, `"DA hash validation OK"` path taken |

Only **one** address family changed materially: the DA2 digest slot moved
`0x2688CC → 0x264C28`, the SHA entry moved `0x2522C4 → 0x24FA00`, and the
allocator/handler code moved by a per-region delta (the binary is a repack, not
a rewrite — see §4).

The only behavioural difference found is *none at the exploit level*: same heap
base/size, same dpc, same forged-node address, same 0x4C parse-scratch chunk,
same exact-fit rule `L = 0x3C`.  The staging address is not hard-coded in the
DA at all: it is the host-supplied `da/arg/at_address` field (0x40000000 in the
command XML), exactly as in 200EX01.

Residual deviations are emulation-only and labelled in §10.

## 2. The digest-slot rule on C.25 (confirmed, not assumed)

DA1's expected-DA2 digest lives at **VA `0x264C28`** (DA1 file offset `0x64C28`,
container offset `0x64CE4`) and the 32-byte value occurs **exactly once** in DA1.

| candidate | length | sha256 | match |
|---|---|---|---|
| `sha256(DA2)` | 0x548C0 | `199a688990e5b39f3a1145b83fdbe7217e5b22e6b6e3fce05ab6df6130396718` | no |
| **`sha256(DA2[:-0x100])`** | **0x547C0** | **`f41b88a302190f18bd5d32ca48c1ebd030208ef429d1723929c04efff8f2fa8e`** | **MATCH** |
| `sha256(DA2[:-0x140])` | 0x54780 | `0370488300ce464f10c0a07d8815f093240e9f443c9d503909a366b85761164c` | no |

So the hashed unit is the **whole DA2 container minus its 0x100-byte signature
trailer** — the same "body excludes the PSS block" rule as 200EX01, where the
body was `0x56EC8` of a `0x56FC8` DA2.

Consequence for the exploit: the digest the stub must write is
`sha256(patched body)` over exactly `0x547C0` bytes, and the patched body must
keep that length.  A one-byte XOR in the 0x18C-byte all-zero gap at DA2
`0x51CBC..0x51E48` works (this is the same structural gap as 200EX01's
`0x543C4..0x54550`, also 0x18C bytes, between pointer tables).  The script uses
`body[0x51D3C] ^= 0x01` (0x80 bytes into the gap, mirroring 200EX01's
`0x54444`) and asserts the byte is zero before patching.

```
old body sha256 : f41b88a302190f18bd5d32ca48c1ebd030208ef429d1723929c04efff8f2fa8e
new body sha256 : fb23f30481c9687ebb30769c3f2cc2367b18914961e6a060edfa6b4e09a50f77
```

```
002012a8  ... "DA Hash mismatch."       (0x251E48, logged on mismatch)
002011ac  ... "DA hash validation OK"   (0x251EAB, logged on success)
```

Findings:

* The staging address is **`da/arg/at_address`** parsed by the host command XML,
  not a constant inside the handler.  `da/arg/jmp_address` becomes `dpc->cb` on
  the success path.  Our `BOOT_XML` sets both to `0x40000000`, which is why a
  failing BOOT-TO leaves the blob at a fixed, known address.
* The handler hashes `[dest, len]` **before** the compare, and the compare loop
  is byte-by-byte with an early exit on the first difference — so a failing
  BOOT-TO returns `0xC0070004` (not the transport error `0xC0010001`).
* `BOOT-TO` does **not** malloc for the staged blob: `download()` sees a
  non-NULL `*dest` and writes straight to `0x40000000`.  It does parse its own
  command XML and frees that tree afterwards, which is why the prelude shifts
  the heap (see §5) without consuming the staging buffer.
* `download` at `0x24D9EC` allocates the *DRAM-REPAIR* buffer with the plain
  heap allocator (thin wrapper `0x204B20` → `0x2040DC`), return address
  `0x24DC38`.  The recv length comes straight from the `packet_length` global
  `0x2DE3F8` and is stored at `0x24DD08` — **unclamped**, the vulnerability is
  present on this build exactly as on 200EX01.

## 5. Heap geometry and the exact-fit rule (sweep)

Declared length `L`; the handler calls `malloc(L+4)`, whose chunk need is
`align4(L+4+0xC) = align4(L+0x10)`.  The fake 12-byte header is written at
`D + (need − 0xC)`, i.e. exactly at the user-capacity boundary; it lands on the
*next chunk's header* only when `malloc` consumes a free node **whole**
(`need == node_size`).  Otherwise `malloc` splits and the header is written into
the fresh free remainder.

Sweep `L=0x20..0x60` step 4, four independent heap histories (fresh emulator per
run; 68 runs).  Representative rows (full table printed by the script):

| history | L | D | chunk | need | fit | victim user | valloc | vfree | fires | state |
|---|---|---|---|---|---|---|---|---|---|---|
| no prelude | 0x20 | 0x2E99E4 | 0x4C | 0x30 | no | 0x2E9A14 | no | no | 0 | no fire |
| no prelude | 0x30 | 0x2E99E4 | 0x4C | 0x40 | no | 0x2E9A24 | no | no | 0 | no fire (split → corrupt remainder, loop guard) |
| no prelude | 0x38 | 0x2E99E4 | 0x4C | 0x48 | no | 0x2E9A2C | no | no | 0 | no fire (loop guard) |
| **no prelude** | **0x3C** | **0x2E99E4** | **0x4C** | **0x4C** | **yes** | **0x2E9A30** | **yes** | **yes** | **1** | **FIRE 0x40000000** |
| no prelude | 0x40 | 0x2EA07C | 0xDF90 | 0x50 | no | 0x2EA0CC | no | no | 0 | no fire |
| failing BOOT-TO | 0x30 | 0x2E9198 | 0x4C | 0x40 | no | 0x2E91D8 | no | no | 0 | no fire (loop guard) |
| **failing BOOT-TO** | **0x3C** | **0x2E9198** | **0x4C** | **0x4C** | **yes** | **0x2E91E4** | **yes** | **yes** | **1** | **FIRE 0x40000000** |
| benign command | 0x3C | 0x2E99E4 | 0x4C | 0x4C | yes | 0x2E9A30 | yes | yes | 1 | FIRE 0x40000000 |
| exact-length download | 0x3C | 0x2E9198 | 0x4C | 0x4C | yes | 0x2E91E4 | yes | yes | 1 | FIRE 0x40000000 |
| any history | 0x40..0x60 | — | 0xDF90 / 0xDDF8 | > 0x50 | no | — | no | no | 0 | no fire |

**Only `L=0x3C` is an exact fit and fires.**  A step-1 fine scan
`L=0x38..0x40` with the BOOT-TO prelude pins the exact-fit window:

```
L = 0x39, 0x3A, 0x3B, 0x3C   -> align4(L+0x10) = 0x4C = chunk -> FIRE
L = 0x38, 0x3D, 0x3E, 0x3F, 0x40 -> no exact fit / no fire
```

Interesting detail from the measurements: for `L=0x30..0x38` the split leaves a
remainder whose header receives the fake `size=0x40000000`, and the *parser*
then loops on the corrupted list (aborted by the harness loop guard — on silicon
this is a dead DA, not a fire).  This is the same failure mode documented for
200EX01: the exact fit is not an aesthetic choice, it is required for survival.

### Parse scratch chunk

The XML parser (`load_str`/mXML at `0x206CC8`) takes `malloc(0x40)` at
`0x206CF8`; its chunk is `align4(0x40+0xC) = 0x4C`.  It holds that chunk for the
whole parse and frees it before the handler's download, which is exactly the
0x4C free node the download malloc consumes whole.

**Measured on C.25: the scratch chunk is 0x4C in every one of the 68+ runs**
(`scratch` column `0x4c`, from the parser `malloc` return read at `ptr−4`).  So
the exact-fit rule is unchanged from 200EX01:

```
L_exact = align4(scratch_req + 0xC) − 0x10 = align4(0x40 + 0xC) − 0x10 = 0x3C
window  : align4(L+0x10) == 0x4C  <=>  L ∈ [0x39..0x3C]
```

## 8. What differs from 200EX01

1. **Addresses** (§4): every function moved, with region-specific deltas.  The
   critical constants that stayed: `dpc 0x2DF7A0`, forged node `0x2DF79C`, heap
   head `0x2DF7D0`, sentinel `0x2DF7D8`, heap arena `0x2E8000/0x10000`,
   `packet_length 0x2DE3F8`.
2. **DA2 slot `0x264C28` and DA2 body `0x547C0`** — the stub and the patch
   offset are the only chain constants that had to change.
3. **SHA entry `0x24FA00`** (still a hardware-engine wrapper, modelled with
   hashlib; the native path produces no digest in Unicorn, probed and reported).
4. **BOOT-TO destination** is `da/arg/at_address` parsed from the command XML in
   *both* builds.  Calling it a "hard-gated 0x40000000" is slightly imprecise:
   the *host* chooses it, the DA trusts it.  This is what makes the staging
   portable; it also means the prelude must use `at_address=0x40000000`.
5. **Exact-fit rule: identical** (`L=0x3C`, parse scratch chunk 0x4C).  No
   reload/retry is needed for C.25.
6. **No tripwire** ("Dest XML file name buffer overflow" string absent) and the
   DRAM-REPAIR command is registered — the vulnerability is present, consistent
   with `da1_static_audit.py`'s VULNERABLE/UNCLAMPED verdict.
7. **Free-list state after the chain** (number of nodes) depends on the heap
   history, but is always walkable to the sentinel and never contains the forged
   node.

## 9. Reload / retry recipe for another build

If a different DA1 repack is dropped in, re-derive in this order; the script's
phase 2/3 does all of it automatically and fails loudly instead of guessing.

1. **Locate the slot**: find the 32-byte value equal to `sha256(da2[:-sig_len])`
   in DA1.  Try `sig_len = 0x100` first (C.25 and 200EX01), then `0x140`.  The
   matching candidate tells you the body length `DA2_BODY`.
2. **Locate the SHA entry and BOOT-TO**: search for a function whose body
   contains `ldrb/ldrb/cmp/bne` over two pointers and a `movw/movt` pair equal to
   the slot VA; BOOT-TO is the caller that calls the download with `&dest` and
   then the SHA routine.  `da1_static_audit.py` resolves this generically.
3. **Heap geometry**: run `heap_init` and read `[head]`, `[head+4]`,
   `[head+8]`, `[head+0xC]`.  Everything (dpc node, sentinel table) follows.
4. **Parse scratch**: hook `malloc`, run one benign command or the DRAM-REPAIR
   handler, and read the chunk size at `ptr−4` for the `malloc(0x40)` issued by
   the XML parser.  Let that be `S`.
5. **Choose L**: `L = S − 0x10` (and verify with a step-1 sweep over
   `[S−0x14, S−0x0C]`).  If `S != 0x4C`, the stub capacity (`S − 0xC` bytes) and
   `DIGEST_OFF` must be chosen so that `stub_len <= DIGEST_OFF < capacity`; keep
   the digest 32 bytes.  The script asserts `STUB_LEN <= DIGEST_OFF` and
   `BLX`-target = `FS_STAGE`.
6. **Re-stage and retry**: if the sweep shows no exact-fit L for any heap
   history, first re-run the *no-prelude* sweep to establish the baseline, then
   add the failing-BOOT-TO prelude.  If the fail is `budget`/corrupted heap, the
   L was too small (split > remainder) — move L up toward `S−0x10`.  If the fail
   is `no fire` with an exact fit, the chunk above the hole is not a live XML
   node: the handler's parse order changed, and the remedy is to stage two
   blobs (double-BOOT-TO) or use the exact-download prelude to shift the hole
   (both are exercised here).
7. **Stub constants**: `FORGED_NODE = dpc−4`, `DPC = dpc`, slot VA, digest VA
   (`FS_STAGE+DIGEST_OFF`).  Re-encode and keep the self-check words list in
   `build_stub()`; it asserts the exact 19 instructions.

No reload is required for C.25.

## 10. Emulation model deviations and limits

* **SHA-256 is modelled with hashlib** at `0x24FA00` (installed hook).  The
  native entry calls `0x2505D0`, which drives the clock gate/engine; the image
  has no software K table.  Probe without the hook: `emu_start returned`,
  PC `0x250DE8`, digest does not match hashlib — i.e. no native digest.  All
  digest values printed by the chain are therefore *model* values, labelled
  `[hashlib]`.
* Everything else is native DA1 code: the BOOT-TO download and compare loop,
  the allocator, the handler dispatch, the XML parser, the fire write, and the
  stub itself.
* The emulator is **stopped at the dpc-clear epilogue `0x200FD0`** immediately
  after the stub returns (a harness exception), so the follow-up probes start
  from the exact post-chain state instead of letting the server loop consume a
  stray handshake packet.  This is a harness stop, not DA1 behaviour.
* Loop guard: a corrupted heap can send the XML parser into a long allocation
  loop.  Runs are aborted after 400 parser-scratch allocations and reported as
  `budget` (no fire) instead of hanging.  On silicon such an L is a dead DA.
* No device, no flashing, no network, no messages were used.
