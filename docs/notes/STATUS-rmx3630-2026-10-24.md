## 3. Где мы (незакрытый вопрос)

После записи зеркала и seccfg телефон **не предъявил Android-композит
`22d9:2046`**. Наблюдения:

- `test11` (запись) → скрипт отправил reboot;
- далее в dmesg только `22d9:0006` (preloader), цикл ~110 с;
- в 22:00 (после hard reset Vol+ + Power) — на USB **вообще ничего**
  (`test13` пуст, `usb_watch.log` без событий);
- вибрация при Vol+ + Power — это аппаратный сброс PMIC, к загрузке отношения
  не имеет.

Рабочие гипотезы, в порядке вероятности:

1. **Телефон просто выключен/в режиме зарядки** (`para` ENV содержит
   `off-mode-charge=1`): preloader от кабеля даёт `0006` и ждёт, а после
   отключения кабеля USB не появляется вовсе. Лечится нажатием Power.
2. **LK выключает телефон** в общем power-off блоке (`0x500557C0`) — например,
   AVB/boot-state «red» при разлоченном состоянии. Тогда в логе будет
   `0006` → `<none>` через 1–3 с.
3. **t-base SFSRP** упал в `Mismatch between the counters` после записи RPMB
   (сдвиг аппаратного счётчика) → TEE/FBE проблемы → загрузка не доходит до
   Android USB. Смягчение: откат зеркала тем же ключом.

Побочно: ранний тест `para` стёр запись `dm_ota=1` из ENV (осталось
`off-mode-charge=1`) — безвредно.

## 7. UPDATE 22:20 (лог `ye`) — два важных факта

### 7.1 Restore-режим был с багом (исправлено)

`MIRROR_RESTORE=1 ./run_rpmb_unlock_mirror.sh` в логе `ye`:

```
[*] current mirror: … locked=0 … hash VALID
[*] saved -> /home/musin/rpmb_mirror_before.bin (md5 11a2d0c1…)   <-- ЗАТЁР оригинал!
[!] restoring the saved mirror block …
[*] write: True
[*] readback identical: True
[*] restored: … locked=0
```

Скрипт сначала сохранял **текущий** (разлоченный) блок поверх «эталонного»
`rpmb_mirror_before.bin`, а потом «восстанавливал» именно его — то есть
восстановление было **холостой операцией**, а эталонный locked=1 блок в этом
файле потерян.

Исправлено:
- в restore-режиме скрипт **не пишет** в `rpmb_mirror_before.bin`;
- источник выбирается из списка и проверяется (`locked==1` + hash valid):
  `MIRROR_RESTORE_SRC` → `/home/musin/rpmb_mirror_before.bin` →
  `/home/musin/rpmb_mirror_locked.bin` → `/home/musin/rpmb_probe_derived.bin`;
- если ни один не подходит, блок **пересобирается** из текущего payload
  (`+0xC=1`, пересчёт SHA-256) — это детерминированно и даёт ровно исходный
  locked-блок;
- обычный режим теперь не перезаписывает эталон, если текущее зеркало не
  `locked=1`.

Эталон сохранён отдельно: `/home/musin/rpmb_mirror_locked.bin`
(md5 `2374972dbf75743b4502861d22d84875`, locked=1, hash valid) — копия

`oplusreserve1[0..0x34]` — это **дескриптор UFS**, а не флаг загрузки:

```
5a3ab79f fae66c7b "YMTC" 00000000
"YMUS8B2TE2A2C1" ... "7.3" ... 0x100000 0x4e96f0c1 0x3aa22bef
```

То есть принт ``l{YMTC``/`YMUS8B2TE2A2C1` — vendor + модель + прошивка накопителя плюс
два 32-битных контрольных значения.

**Код:** `0x500053E0` (её вызывает `boot_mode_check` @0x5000AE50) на успешном
пути делает `mov w0, wzr` (0x50005564), а отрицательные коды (−0x13/−8) — только
при ошибке open/read. В boot_mode_check: `cbz w0` → режим не меняется,
иначе `mode = 2 (RECOVERY)`. Наш раздел читается (197 ненулевых байт) ⇒
**recovery-ветка не срабатывает**, флага boot-fail там нет.
(Нюанс: LK читает 0x34 байта по смещению `[part+0x28]*0x438`, а не с нуля —
наш дамп снял копию дескриптора по смещению 0. Для полноты можно дочитать.)

`misc`: BCB пуст (нет `boot-recovery`), BCAB валиден, но **6 байт отличаются** от
предкампанийного бэкапа (0x80C/0x80E/0x81C–0x81F = слот/чексумма) ⇒ LK уже
писал сюда после начала кампании. `expdb` пуст, `boot_para` нулевой.

**Вывод:** во флеше нет ни одного признака «загрузка провалилась». Значит
сбой — после LK: либо LK уходит в power-off по boot-state, либо ядро/Android
не доходит до USB.

### 8.2 Разбор трёх гипотез

| гипотеза | вердикт |
|---|---|
| **H1. Orange State ждёт физическую кнопку** | **Опровергнуто кодом.** Баннер Orange (0x50053F78) печатает «…will boot in 5 seconds» и делает фиксированный `mdelay`; опроса кнопок в этом пути нет. Power-off блок — тоже `mdelay(0x2DC6C0)` + выключение. |
| **H2. Запись RPMB сдвинула аппаратный счётчик → t-base SFSRP fatal → TEE/FBE** | **Правдоподобно, ведущая гипотеза.** Счётчик сдвинулся нашей записью; SFSRP сверяет `stored+1` со своим счётчиком и падает в `Mismatch between the counters`, после чего trustedStorage/Keymaster недоступны, а без них не расшифровывается userdata (FBE) — Android не доходит до USB. Прямого подтверждения пока нет. |
| **H3. Стоковый boot несовместим с `lock=3` без dm-verity** | **Механизма не видно**, но есть реальная аномалия: у нас `lock_state=3` при `sboot_runtime=0`, и зеркало `locked=0` при `sboot=0`. Настоящий unlock (`fastboot flashing unlock`) пишет `sboot=1` и в seccfg, и в зеркало. Комбинация «неестественная», её стоит проверить отдельным вариантом. |

### 9.2 Дефект методики: при подключённом USB preloader ЖДЁТ DA

Все наблюдения «после ребута нет Android, висит `22d9:0006`» **невалидны**:
на этом аппарате, если кабель подключён в момент старта, preloader останавливается
в VCOM-режиме и ждёт DA вместо продолжения загрузки (это было зафиксировано ещё
в начале кампании и затем забыто). Поэтому:

- после `loader.shutdown(...)` кабель остаётся в порту → preloader ждёт → `0006`
  висит сколько угодно;
- `2046` в этой схеме не появится **никогда**, даже если Android полностью
  исправен.

Правильная проверка загрузки:

```
1) DA-сессия завершается ребутом  ->  СРАЗУ выдернуть кабель (1-2 с)
2) подождать 60-90 с (идёт загрузка, кабеля нет)
3) вставить кабель  ->  смотреть lsusb:
      22d9:2046 = Android поднялся
      18d1:…    = fastboot
      ничего    = телефон выключился/не стартовал
```

## 11. UPDATE 23:25 — что делает НАСТОЯЩИЙ unlock в этом LK

Дизасм fastboot-обработчика unlock `0x500076A8`:

```
0x500077fc bl 0x500323D4            ; get/set? (args)
0x50007804 bl 0x5003266C           ; -> 0x50082E88(0) = sec_cfg_set_lock_state(UNLOCK) -> 3
0x50007834 bl 0x50007C9C           ; *** WIPE userdata/metadata ***
0x500078e0 mov w0,#1 ; mov w1,#1
0x500078e8 bl 0x50054744           ; set_boot_info_to_rpmb(sboot=1, flag=1) -> mirror: sbc=1, locked=0
```

Два следствия:

1. **Официальный unlock стирает userdata/metadata** (`0x50007C9C`). Мы этого не делали.
2. Официальный unlock пишет в зеркало `sboot=1` (sbc bit), а не 0, как у нас.

Почему это важно: если ключи FBE/Keymaster привязаны к состоянию блокировки
(типовая причина, по которой OPPO и стирает данные при unlock), то после смены
`lock_state` 4→3 старая `/data` не расшифровывается — Android не доходит до
готовности, ядро/init падает, и мы видим именно то, что видим: пара вибраций
(старт → сброс) и отсутствие `2046`.

То есть **наш unlock был «неполным»**: без вайпа и с `sboot=0` в зеркале.
Это не значит, что данные обязательно потеряны, но проверить гипотезу можно
только стиранием (или чтением NoBoot-счётчика — см. `reserve1_probe.py`).

## 12. UPDATE 23:40 — план: вайп данных (как штатный unlock)

Симптом: при разлоченной загрузке — один короткий «старт» и сброс (двойная
вибрация), цикла нет (вибрация повторяется только при форс-ребуте). Значит
имеем одну неудачную попытку загрузки, а не bootloop предзагрузчика.

Данные пользователю не нужны ⇒ делаем ровно то, что делает штатный unlock:
стереть `userdata` + `metadata`.

Инструмент: `wipe_and_unlock.py` (`./run_wipe_and_unlock.sh`, запись только с
`WIPE_GO=1`; обёртка выставляет `OPLUS_PATCH_ERASE_DENY=1`, иначе DA блокирует
ERASE-FLASH):

1. читает и печатает состояние (`seccfg lock`, зеркало `locked`);
2. `ERASE-FLASH` для `metadata` (полностью, 32 МБ) и `userdata` (полностью,
   UFS unmap; при неудаче — обнуление первых 16 МБ, этого достаточно, чтобы
   убить суперблоки f2fs/ext4);
3. если `seccfg` не 3 — пишет unlock-образ; если зеркало не `locked=0` —
   пишет разлоченный блок;
4. **не перезагружает** (иначе preloader снова встанет ждать DA) и печатает
   инструкцию: выдернуть кабель → Power 10 с → Power 3 с → 90–120 с без кабеля
   → вставить кабель → `lsusb`.

Первый старт после вайпа может занять 2–3 минуты (форматирование /data).

## 14. ПРОРЫВ: Android загрузился, ADB включён (2026-10-25 00:05)

После вайпа `metadata` (1 МБ) + `userdata` (16 МБ) и правильного включения
(кабель выдернут) устройство поднялось:

```
22d9:2769  RMX3630  Serial SG7DCQW8X8ONCI9T
  bInterfaceClass 255 / SubClass 66 / Protocol 1  ->  "ADB Interface"
adb devices -> SG7DCQW8X8ONCI9T   unauthorized
```

То есть:

1. **Гипотеза о привязке ключей FBE к lock_state подтвердилась**: без вайпа
   разлоченная система не стартовала, после вайпа — стартует.
2. **adbd работает**, USB-конфиг = ADB. Осталось авторизовать хост: диалог
   «Allow USB debugging» на мёртвом экране не нажать.

### Решение: патч boot-рамдиска

`boot.img` разобран: header **v3/v4** (`kernel_size=0x1376ecd`,
`ramdisk_size=0x192c75`, `header_size=0x630`), рамдиск — **LZ4-legacy** на
`0x1378000`, внутри newc-cpio из 15 записей (`init`,
`system/etc/ramdisk/build.prop`, …).

`boot_ramdisk_patch.py` (собственный LZ4-legacy кодек + cpio reader/writer):

* правит `system/etc/ramdisk/build.prop`:
  `ro.adb.secure=0` (adbd принимает любой хост), `ro.debuggable=1` (adbd root),
  `persist.sys.usb.config=adb` (USB=ADB на первом буте);
* добавляет `/adb_keys` с публичным ключом хоста;
* пересобирает образ: тот же header, kernel 20 МБ, новый LZ4-рамдиск
  (`0x3035af`), итог `0x167c000` B → `/home/musin/boot_patched.img`.

`flash_boot_patched.py` (`./run_flash_boot_patched.sh`, запись только с
`FLASH_GO=1`): полный бэкап `boot_a` (64 МБ) → запись → readback+md5.
Откат: `BOOT_RESTORE=<backup> FLASH_GO=1 ./run_flash_boot_patched.sh`.

Риск: изменённый boot не совпадёт с хешем в vbmeta (AVB). При `lock=3`
(orange) LK обычно допускает ошибку верификации; если нет — откат одним
запуском.
