## Контракты задач

### A. Q1: vendor_boot forensics (`vendor_boot_extract.py` + `re-vendor-boot-q1.md`)
Гипотеза Q1 (единственная причина провала v5): исполняется `init` из vendor_boot, а не из boot.
Ответить фактами: есть ли в vendor_boot `init` / `force_debuggable` / `adb_debug.prop`,
какой набор (platform set), чем сжат, что в bootconfig. Сравнить init из boot-рамдиска
(ожидается 3 143 536 B) и из vendor_boot. Дать вердикт: чей `/init` первым попадает в rootfs
и что именно надо править в следующей v6.
Приёмка: `--info`, `--list`, `--extract` на реальном `vendor_boot.img` дают exit 0; в логе — таблица
фрагментов, sha256 каждого найденного `init`, размеры и кодеки.

### B. Q2: property gate в init (`re-init-prop-gate.md`)
На `init` из boot-рамдиска (3 143 536 B) и, если удастся достать, на `/system/bin/init`
(3 085 160 B): идентифицировать функцию `0x2D81A0` (в system-init) по строкам
"Do not have permissions to set" / `property_set_fd` / xref на `/debug_ramdisk/adb_debug.prop`,
ветку `0x158C80`, и `load_properties_from_file`. Ответить: может ли `ro.adb.secure=0` из
`adb_debug.prop` примениться на user-сборке; если нет — минимальный патч init (адрес, байты
до/после) и ожидаемый эффект.
Приёмка: `r2`/`objdump`-лог с адресами и xref; патч-спека проверена скриптом: применяем на копию,
diff ровно N байт, `readelf -h` по-прежнему парсит ELF.

### C. Q3: system.img + adbd APEX fallback (`re-adbd-apex-route.md` + unsparse/EROFS reader)
Достать из sparse `system.img` (`/system/apex/com.google.android.adbd.apex`, `/system/build.prop`,
`/system/etc/selinux/plat_property_contexts`). Оценить: можно ли подменить adbd внутри APEX на
user-сборке (подпись APEX, apexd, `ro.apex.updatable`, ключи в `/system/etc/security/apex`).
Вердикт «да/нет» + какая конкретно проверка блокирует.
Приёмка: лог извлечения файлов с sha256; цитаты строк/файлов для каждого вывода. Если EROFS-ридер
не осилен — честно `BLOCKED` с указанием, что нужно (`erofs-utils`) и что уже проверено.

### E. (раунд 2) LK ground truth: initrd order + verifiedbootstate
Конфликт: A говорит «исполняется boot-/init», B нашёл второй гейт
`env=="true" && IsDeviceUnlocked()` (`verifiedbootstate=="orange"`) в `SecondStageMain`.
STATUS §19.1 утверждает, что orange для adb_debug.prop не нужен — это опровергнуто
дизасмом system-init. Значит либо orange не выставляется, либо boot-/init не исполняется.
Ответить по `docs/notes/rmx3630-lk/lk_payload.bin` (base 0x40000000): порядок склейки
initrd, адрес initrd-start/end, где LK дописывает bootconfig; условие и таблица маппинга
boot_state (lock=3 → ?), активен ли путь записи `androidboot.verifiedbootstate`;
зависит ли `img_auth_required` от lock_state для boot **и** vendor_boot.
Приёмка: r2-лог с адресами, вердикт-таблица, предсказание для v6.

### F. (раунд 2) v6 dual-patch builder без устройства
`docs/notes/build_v6_dual.py`: из стока boot.img (репо) и стока vendor_boot.img (/tmp/fw)
собрать `/tmp/v6/boot_v6.img` + `/tmp/v6/vendor_boot_v6.img`: P1 (boot init 0xF6D14),
P2 (vendor init 0xF1710), маркер `/force_debuggable` + `/adb_debug.prop` в оба рамдиска,
vbmeta/футер boot побайтно стоковые, таблица/смещения vendor_boot пересчитаны, dtb
неизменён. Плюс верификатор всех инвариантов (PASS/FAIL, exit 0 только при PASS)
и flash/rollback инструкция. Ничего не флешить.

### D. Verification harness (device-side, сейчас заглушка)
`docs/notes/verify_adb_state.sh`: на Termux-хосте после прошивки собрать: `lsusb`-эквивалент
(`/sys/bus/usb/devices`), `adb devices -l`, `adb get-state`, `adb shell getprop ro.adb.secure`
(если authorized), `/proc/cmdline` и bootconfig через `adb shell cat /proc/cmdline` (если root),
плюс чеклист «что смотреть, если снова unauthorized». Плюс `--dry-run` (по умолчанию) для
локальной проверки без устройства.
Приёмка: `bash -n`, `--help`, `--dry-run` дают exit 0; вывод читаемый.
